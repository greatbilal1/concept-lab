Introduction: why object-oriented programming matters

Before we write a single class, it is worth asking why object-oriented programming exists at all. OOP is not a syntax feature you learn for its own sake — it is a way of organising software so that it stays understandable as it grows.

The core problem OOP solves: as a program grows, the number of moving parts grows faster than the number of lines of code. Without structure, a small script becomes a tangle where changing one thing breaks three others. OOP gives you a way to draw boundaries — so each part of the system has a clear job and a clear place to live.

What is object-oriented programming?

OOP is a style of programming that organises code around objects rather than around a long sequence of instructions. An object bundles together:

📦

State

The data an object remembers — a customer's name, an account's balance, a game character's health.

⚡

Behavior

The operations the object can perform — deposit money, calculate risk, take damage.

🔒

Boundaries

Rules about how that state may change, kept close to the data itself instead of scattered everywhere.

Why do people use OOP?

  • It models the real world. Most problems are naturally described in terms of things — customers, orders, accounts, players. OOP lets the code mirror the way you already think about the problem.
  • It manages complexity. By grouping related data and behavior, you can reason about one piece at a time instead of holding the whole program in your head.
  • It reduces duplication. Inheritance and composition let you write shared behavior once and reuse it, instead of copy-pasting and letting copies drift apart.
  • It makes change safer. When rules live inside the object that owns the data, you change them in one place — and the rest of the system keeps working.
  • It enables teamwork. Clear objects with clear responsibilities are easier for several people to work on at the same time without stepping on each other.
  • It is everywhere. Python's own standard library, web frameworks, game engines and data tools are all built on these ideas. Understanding OOP is understanding the code you will actually read.

Where OOP is used

🌐

Web & APIs

Frameworks model requests, users, sessions and database rows as objects.

🎮

Games

Characters, weapons, levels and physics bodies are all objects with state and behavior.

📊

Data & ML

Models, datasets, pipelines and metrics are represented as reusable objects.

🏦

Business systems

Accounts, transactions, customers and risk rules map cleanly onto classes.

4. __init__: initializing an object

__init__ runs automatically when an object is created.

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

account = BankAccount("Bilal", 1000)

Conceptually Python creates the object and then calls the initializer with that object as self.

Common misconception: __init__ initializes an already-created object; it is not technically the object's creation mechanism.

5. Methods: what objects can do

class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        if amount <= self.balance:
            self.balance -= amount
        else:
            print("Insufficient funds")

account = BankAccount("Bilal", 1000)
account.deposit(500)
account.withdraw(200)
print(account.balance)

Methods normally receive self first so they can access the particular object they are operating on.

Pattern: object.method(value) → Python supplies the object as self.

6. Encapsulation

Encapsulation means keeping related state and behavior together and controlling how state is changed.

class BankAccount:
    def __init__(self, balance):
        self.balance = balance

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("Amount must be positive")
        if amount > self.balance:
            raise ValueError("Insufficient funds")
        self.balance -= amount

Instead of allowing every part of your application to implement withdrawal rules, the account owns those rules.

Python does not enforce private fields in the same way some languages do. A leading _ is mainly a convention; __name triggers name mangling.

7. Inheritance

Inheritance lets one class derive behavior from another.

class Customer:
    def __init__(self, name):
        self.name = name

    def introduce(self):
        return f"I am {self.name}"

class BusinessCustomer(Customer):
    def __init__(self, name, company):
        super().__init__(name)
        self.company = company

c = BusinessCustomer("Bilal", "ABC Bank")
print(c.introduce())
print(c.company)

8. Polymorphism

Polymorphism means different objects can provide the same interface while behaving differently.

class IndividualCustomer:
    def risk_type(self):
        return "Individual risk model"

class BusinessCustomer:
    def risk_type(self):
        return "Business risk model"

customers = [IndividualCustomer(), BusinessCustomer()]

for customer in customers:
    print(customer.risk_type())
Duck typing: Python often cares less about an object's class and more about whether it supports the operation you need.

9. Abstraction

Abstraction means exposing the important interface while hiding implementation details.

from abc import ABC, abstractmethod

class RiskModel(ABC):

    @abstractmethod
    def calculate(self, customer):
        pass

class KYCModel(RiskModel):

    def calculate(self, customer):
        return customer.risk_score * 1.2

The user of KYCModel can call calculate() without needing to know every internal detail.

Interface idea: “This object promises to provide calculate().”

10. Composition — objects containing other objects

Composition models a “has-a” relationship.

class Address:
    def __init__(self, country, city):
        self.country = country
        self.city = city

class Customer:
    def __init__(self, name, address):
        self.name = name
        self.address = address

address = Address("Sweden", "Stockholm")
customer = Customer("Bilal", address)

print(customer.address.city)

Rule of thumb: inheritance is often “is-a”; composition is “has-a”. Composition is frequently more flexible.

11. Special / dunder methods

Methods surrounded by double underscores are called special methods or “dunder” methods.

class Customer:
    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"Customer: {self.name}"

    def __repr__(self):
        return f"Customer({self.name!r})"

c = Customer("Bilal")
print(c)

12. Properties

A property lets you expose method-backed logic as if it were an attribute.

class BankAccount:
    def __init__(self, balance):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("Balance cannot be negative")
        self._balance = value

account = BankAccount(1000)
account.balance = 1500
print(account.balance)

This gives you a clean API while allowing validation behind the scenes.

13. Instance, class and static methods

Instance method

def deposit(self, amount):
    self.balance += amount

Works with a particular object.

Class method

@classmethod
def from_json(cls, data):
    return cls(data["name"])

Receives the class as cls. Useful for alternate constructors.

Static method

@staticmethod
def is_valid_country(code):
    return len(code) == 2

Related to the class but doesn't need the instance or class.

Rule

Use an instance method when behavior needs object state; a class method when behavior concerns the class/constructing instances; a static method for a utility logically grouped with the class.

14. Dataclasses

When a class mainly stores data, dataclass can remove boilerplate.

from dataclasses import dataclass

@dataclass
class Customer:
    name: str
    country: str
    risk_score: int

customer = Customer("Bilal", "SE", 85)

print(customer)
print(customer.risk_score)

Python automatically provides useful methods such as an initializer and readable representation.

15. Designing an OOP system

Before writing classes, break the problem into concepts.

Step 1 — Identify nouns

Customer, Account, Transaction, Alert, Investigation.

Step 2 — Identify data

Customer ID, country, balance, amount, risk score.

Step 3 — Identify actions

Deposit, withdraw, calculate risk, create alert.

Step 4 — Identify relationships

Customer has Accounts. Account has Transactions. Investigation contains Alerts.

Avoid over-engineering: Not every noun needs a class. OOP is a tool, not a requirement. Simple data can sometimes remain simple data.

16. Complete practical example: KYC risk model

Here is a small domain model showing several OOP ideas together.

from dataclasses import dataclass

@dataclass
class Customer:
    customer_id: str
    country: str
    risk_score: int

    def is_high_risk(self):
        return self.risk_score >= 70


class RiskModel:

    def calculate(self, customer):
        score = customer.risk_score

        if customer.country in {"XX", "YY"}:
            score += 20

        return min(score, 100)


customer = Customer(
    customer_id="C001",
    country="SE",
    risk_score=65
)

model = RiskModel()
score = model.calculate(customer)

print("Final score:", score)
print("High risk:", score >= 70)
Architecture lesson: The Customer represents customer state and basic customer behavior. The RiskModel represents a separate responsibility: calculating risk.
