Lesson 06 · Raising

Custom exception types

Built-in exceptions cover common failures, but a library or application may have a meaningful domain failure of its own. A custom exception gives callers a stable name they can catch without parsing message text.

Time ~10 min Win Define an exception callers can catch by name Mission link Give expected failures a clear contract

1Name a domain failure

A stock lookup can fail because the requested item is not available. A caller may want to handle that differently from a broken file path or a programming error. Define a small exception that names this one condition: 

class OutOfStockError(Exception):
    """Raised when an item cannot be supplied."""

def reserve(item):
    if item.stock == 0:
        raise OutOfStockError(f"{item.name} is unavailable")
Key idea A custom exception is a catchable type for a failure meaningful to your program; it is not just a custom message string.

2Second idea

2Join Python's exception tree

Subclass Exception for ordinary application failures. Then callers can catch your type specifically, while a broader handler for Exception can still catch it when that is appropriate. Avoid subclassing BaseException: that branch also contains interpreter-control signals such as KeyboardInterrupt and SystemExit, which normal application handlers should not swallow.

3Third idea

3Catch the type, not its wording

Message text is for people and may change as the program improves. The type is the contract for code. A caller can handle the named failure and let unrelated exceptions propagate as before.

4Practice

Recall the key facts from memory before the quiz.

✓ Your win for today You can define a focused exception under Exception, raise it when a domain condition occurs, and let callers handle it by type rather than matching fragile message text.
