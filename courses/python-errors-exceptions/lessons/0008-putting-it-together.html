Lesson 08 · Putting it together

Putting it together

A reliable function does not pretend every operation succeeds. Put the earlier ideas together: validate and raise close to the cause, clean up resources with with, and translate expected failures once at a boundary that can explain what the program can do next.

Time ~10 min Win Build a small, explicit failure path Mission link Make failure predictable and recoverable

1Separate work from the boundary

A low-level function should do the work and raise meaningful exceptions; it should not decide how a command-line app, web route, or user interface explains every possible failure. The outer boundary knows what response is appropriate. Catch expected failures there, not around the whole program.

Key idea Catch an exception at the lowest layer that can recover meaningfully, or at the outer boundary that can report it clearly; let unrelated failures show.

2Second idea

2Let the context manager clean up

File handles and similar resources need cleanup on both success and error. Use a with statement rather than manually remembering to close a file in every branch. The context manager's exit logic runs as control leaves the block, including when an exception is propagating.

3Third idea

3Make the whole path visible

This small command-line style example keeps the original cause attached with raise ... from. The outer layer handles only the failures it can explain. A retry belongs only around a plausibly transient operation, must be bounded, and is omitted here because reading a local file or parsing its contents is not made reliable by repeating it.

4Practice

Recall the key facts from memory before the quiz.

✓ Your win for today You can trace a failure from its cause through cleanup to a deliberate boundary, preserving context and producing a useful outcome without swallowing unrelated bugs.

5Do this next

  1. Write a function that reads a number from a text file using with and raises ValueError for invalid contents.
  2. At the caller, handle only FileNotFoundError and ValueError with separate messages.
  3. Translate a low-level failure with raise RuntimeError(...) from error, then inspect the chained traceback.
