Lesson 02 · Tracebacks

Reading a traceback

Last lesson you learned that an exception is an object travelling up your call stack. When nobody catches it, Python prints a report of that journey. This lesson teaches you to read that report from the bottom up — because the last line is the answer, and everything above it is the route.

Time ~10 min Win Find the failing line in any traceback in seconds Mission link Debugging starts with reading, not guessing

1The report has a shape

Here is a traceback you have probably seen. It looks like noise, but it has three distinct parts, and each one answers a different question. 

Traceback (most recent call last):
  File "app.py", line 12, in <module>
    report([])
  File "app.py", line 8, in report
    return average(nums)
  File "app.py", line 4, in average
    return sum(nums) / len(nums)
ZeroDivisionError: division by zero

The first line is a header. The middle is a list of frames — one per function call, oldest first. The last line names the exception type and its message. That last line is the single most important line on your screen.

Key idea Read a traceback bottom-up: the last line tells you what went wrong, and the frame just above it tells you where.

2Frames are a call stack

Each block in the middle is a frame: a file, a line number, a function name, and the source line that was executing. The frames are printed in the order the calls happened, so the last frame is the deepest call — the one that actually raised.

That is why the header says "most recent call last". The list reads like a stack of plates: the bottom plate was placed first, and the top plate is the one you touch. The top of the stack is where the exception was born.

In Lesson 01 you watched an exception travel up this exact stack. The traceback is simply the receipt for that journey, printed after the fact.

3Watch the frames build

Step through this program. Each call pushes a new frame; when the division fails, the traceback is the list of frames still on the stack.

Notice that the failing line is the deepest frame, and the entry point is the shallowest. When you read a real traceback, start at the bottom and walk up only as far as you need to understand the cause.

4Practice

Recall the key facts from memory before the quiz.

✓ Your win for today

You can now open any traceback and go straight to the last line for the exception type and message, then read the frame above it for the exact file and line. No more scrolling through red text hoping to spot the problem.

5Do this next

  1. Run the average([]) example yourself and count the frames. Confirm the deepest frame is the line that divides.
  2. Deliberately misspell a variable name and read the NameError traceback. Find the line number it points at.
  3. Take a traceback from a program with three nested functions and write down, in order, the function names from shallowest to deepest.
