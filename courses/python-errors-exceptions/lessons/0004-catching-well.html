Lesson 04 · Catching

Catching well

You can catch an exception now. But catching is easy to get wrong in ways that hide bugs for months. This lesson is about the three habits that separate a handler that helps from one that hurts: catch narrowly, clean up with finally, and never swallow a failure silently.

Time ~10 min Win Write handlers that do not hide real bugs Mission link Failure you can trust is failure you can fix

1The bare except trap

The quickest way to make an error go away is except: with no type. It catches everything — including the mistakes you did not expect and the ones you cannot fix. That is not handling; it is hiding. 

try:
    total = price / count
except:
    total = 0

If price is misspelled, this code does not tell you. It quietly sets total to zero and carries on with wrong data. A NameError that should have stopped you at line one now corrupts everything downstream.

Key idea Catch the narrowest type you can name. A bare except: catches bugs you never meant to handle.

2finally always runs

Some work must happen whether or not the risky part succeeded — closing a file, releasing a lock, rolling back a transaction. That is what finally is for. It runs after the try block finishes, after any handler, and even if the block returns.

There is also an else block, which runs only when the try succeeded. Together, try, except, else, and finally give you a place for every outcome.

4Practice

Recall the key facts from memory before the quiz.

✓ Your win for today

You can now name the exact exception you expect, guarantee cleanup with finally, and recognise a bare except: as the bug it usually is. Your handlers will surface problems instead of burying them.

5Do this next

  1. Take a bare except: from your own code and replace it with the specific type you actually expect.
  2. Add a finally block that prints "done" and confirm it runs whether the try succeeds or fails.
  3. Add an else block and confirm it runs only on success, never when the handler fires.
