Lesson 05 · Raising

Raising your own

In the last lessons, Python raised exceptions while your code was running. You can also raise one when your function detects an invalid value or an impossible state, stopping bad data at the boundary where it first appears.

Time ~10 min Win Reject invalid input with a useful exception Mission link Make failure explicit at its source

1Stop a bad value early

Imagine a function that divides a total among a number of people. A zero count is not a meaningful request. If the function lets it travel deeper, the eventual division error is farther from the bad input. Validate the argument where the function receives it: 

def split_bill(total, people):
    if people <= 0:
        raise ValueError("people must be greater than zero")
    return total / people
Key idea Raise an exception when a function cannot honor its contract; do not return a plausible-looking value that hides invalid input.

2Second idea

2Choose a type that says what failed

Use ValueError when the type is acceptable but the value is not (a negative number of people). Use TypeError when the kind of object is wrong. Python's built-in exceptions already give callers useful categories, so prefer them when they describe the failure accurately. Raising does not print a message or decide how the program recovers: it creates an exception and starts the same propagation you traced in Lesson 01.

3Third idea

3Follow the failure to its handler

A guard clause checks an assumption before the main work begins. If the caller chooses to recover, it catches the named exception; otherwise the traceback keeps the failure visible.

4Practice

Recall the key facts from memory before the quiz.

✓ Your win for today You can reject invalid input early, choose a built-in exception that names the problem, and leave recovery to the layer that can make a useful choice.

5Do this next

  1. Write a function that accepts a percentage and raises ValueError outside 0 through 100.
  2. Add a guard clause for a missing required name and include the name in its error message.
  3. Call the function inside a narrow handler and show a friendly response without catching unrelated bugs.
