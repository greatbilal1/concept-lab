Lesson 04 · Small Functions & Guards

Command Query Separation and side effects

Asking a question shouldn't change the answer. Discover Bertrand Meyer's Command Query Separation (CQS) principle and eliminate hidden side effects.

Time ~10 min Win Enforce Command Query Separation to eliminate hidden mutation side effects Mission link Prevents subtle bugs where reading data unexpectedly mutates system state

1Asking a question must not change state

Bertrand Meyer introduced the Command Query Separation (CQS) principle: every method should either be a Command (performs an action and mutates state, returning void) OR a Query (calculates and returns data, with zero side effects).

A function called is_valid_user() should never secretly update the user's password or send an email! When queries cause hidden side effects, developers cannot trust their code to inspect state without accidentally triggering mutations.

Key idea Commands change state but return void; Queries return data but cause zero side effects.

2Command versus Query contract

Understand the strict separation between state mutators and observational queries.

3Tracing CQS refactoring

Trace how separating a getter from a mutator makes code predictable and testable.

4Practice

Test your memory of Command Query Separation.

✓ Your win for today

You can write predictable functions following CQS that do not cause hidden state mutations when queried.

5Do this next

  1. Audit a function in your codebase that returns data while secretly modifying state.
  2. Refactor it into two explicit functions: a command and a query.
  3. Ensure all getter functions in your classes are pure and idempotent.
Primary source Bertrand Meyer, *Object-Oriented Software Construction* (Prentice Hall, 1988).
