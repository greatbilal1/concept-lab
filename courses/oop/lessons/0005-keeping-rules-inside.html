Lesson 05 · Protecting state

Keeping rules inside

Encapsulation is not about secrets — it is about control. When the only way to change an attribute is through a method that checks the rules, the object can never end up in a broken state.

Time ~10 min Win Make an object impossible to break Mission link Rules enforced in one place

1The problem with open attributes

Right now anyone can reach in and set anything. 

book = Book("Dune", 3)
book.copies = -99        # nothing stops this
book.copies = "lots"     # nor this

The object has no say in its own state. Every caller has to remember the rules, and one of them will forget.

The failure When state can be changed from anywhere, the rules about that state are spread across the whole program. There is no single place to look, and no single place to fix.

2Mark it private, change it through a method

Python's convention: a leading underscore means "internal — do not touch from outside". Then provide a method that enforces the rule. 

class Book:
    def __init__(self, title, copies):
        self.title = title
        self._copies = copies          # internal

    def restock(self, n):
        if n < 0:
            raise ValueError("cannot restock a negative amount")
        self._copies += n

    @property
    def copies(self):                  # read-only view
        return self._copies
Key idea The underscore says "this is mine". The method is the only door into the state, and it checks the rules on the way in.

3Python's honesty about privacy

Python does not truly hide anything. The underscore is a promise, not a lock. That is deliberate: it trusts you to respect the boundary.

NameMeaning
copiesPublic — safe to use from outside.
_copiesInternal — do not touch from outside.
__copiesName-mangled — for avoiding clashes in subclasses.
Do not overdo it Encapsulation is for state that has rules. A plain data holder with no invariants does not need getters and setters — that just adds noise. Protect what needs protecting.
