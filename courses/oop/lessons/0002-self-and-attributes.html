self and attributes

self is the first thing that confuses everyone. It is not a keyword and not magic — it is just the object the method was called on, handed in automatically. See that once and attributes fall into place.

Time ~8 min Win Read self.x correctly, every time Mission link Each object keeps its own state

1Two objects, two states

Build two books from one class, then change one. Watch the other. 

class Book:
    def __init__(self, title, copies):
        self.title = title
        self.copies = copies

a = Book("Dune", 3)
b = Book("Neuromancer", 1)

a.copies -= 1

print(a.copies)   # 2
print(b.copies)   # 1  — untouched

Each object carries its own title and copies. These are attributes (also called instance variables). Changing a never touches b — that separation is the whole reason objects exist. The Python Tutorial on instance objects states it plainly: instance attributes are stored per object, not on the class.

Key idea Attributes live on the object. Two objects from one class are two separate bundles of state.

2What self actually is

Here is the trick that makes self click. These two lines do the exact same thing: 

a.borrow()          # the normal way
Book.borrow(a)      # what Python really does

When you write a.borrow(), Python looks up borrow on the class and calls it with a as the first argument. That first argument is what we name self. It is an ordinary parameter — you could name it anything, but the whole community calls it self (PEP 8 makes it a convention, not a rule).

The rule self is the object the method was called on. Inside the method, self.title means "the title of this particular object".

3Reading and writing attributes

Inside a method you reach attributes through self. Outside, you reach them through the object's name.

WhereHow you write it
Inside a methodself.copies
Outside, on an objecta.copies
On the class (shared)Book.copies — usually a mistake
Common trap Forgetting self. inside a method creates a local variable that vanishes when the method ends. The attribute never changes. If a method "does nothing", look for a missing self..

✓ Your win for today

You can now read self.x as "the x of the object this method was called on", and you know a.borrow() is really Book.borrow(a). That one reframing removes the biggest early source of confusion in Python OOP — and it is exactly the mental model you need when your project's classes start holding real state.
