What an object actually is

Before classes, before self, before inheritance — there is one idea. An object is data that carries its own behaviour. Get this and everything else in OOP is a variation on it.

Time ~10 min Win Build and use your first object Mission link Boundaries that keep a growing project readable

1The problem with loose data

Imagine you are building the project from your mission — say a small library catalogue. You start the obvious way: a dictionary per book. 

book = {
    "title": "Dune",
    "author": "Herbert",
    "copies": 3,
}

print(book["title"])   # Dune

This works. But the data and the rules about the data live in different places. Nothing stops this: 

book["copies"] = -5          # a book with negative copies?
book["titel"] = "Dune"       # typo — silently creates a new key
print(book["copies"])        # -5, and nobody complained
The failure The dictionary has no opinion about what a book is. Any key, any value, any time. As the project grows, every part of the code has to remember the rules — and one part will forget.

2An object bundles data with its rules

An object is a bundle of two things that belong together:

  • State — the data it remembers (title, author, copies).
  • Behaviour — the operations it can perform (borrow(), restock()).

The behaviour is the part dictionaries cannot give you. It is where the rules live — right next to the data they protect.

Key idea An object is state + behaviour in one unit. The state is what it knows; the behaviour is what it can do. Always picture both together.

3Your first object

Here is the same book, as an object. Read it slowly — every line is doing something specific. 

class Book:
    def __init__(self, title, author, copies):
        self.title = title
        self.author = author
        self.copies = copies

    def borrow(self):
        if self.copies <= 0:
            return "No copies left"
        self.copies -= 1
        return f"Borrowed {self.title}"


dune = Book("Dune", "Herbert", 3)
print(dune.borrow())    # Borrowed Dune
print(dune.copies)      # 2

Three things just happened, and they are the whole of OOP in miniature:

LineWhat it does
class Book:Defines the blueprint — what every book will have.
dune = Book(...)Builds one object from the blueprint.
dune.borrow()Calls the object's behaviour, which changes its own state.
Why this is better The rule "you cannot borrow a book with zero copies" now lives inside borrow(). No caller can bypass it. Change the rule once, and every part of the program obeys.

✓ Your win for today

You can now explain, in your own words, why an object beats a loose dictionary: it keeps the rules next to the data. That single idea is the reason OOP exists, and every later lesson — self, inheritance, composition — is a way of organising that bundle better.

5Do this next

  1. Open a Python REPL (python3 in a terminal) and type the Book class above by hand. Do not copy-paste — typing it is the practice.
  2. Add a restock(self, n) method that adds n copies. Call it, then print dune.copies.
  3. Break it on purpose: call dune.borrow() four times in a row. What happens on the fourth call? Why is that better than the dictionary silently going negative?
