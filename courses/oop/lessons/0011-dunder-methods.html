Dunder methods

Dunder methods (double underscore, like __init__) let your objects plug into Python's own syntax. Define __len__ and len(obj) works. Define __eq__ and == works. Your objects stop feeling foreign.

Time ~10 min Win Make your objects behave like built-ins Mission link Objects that fit the language

1Your object feels foreign

Print a plain object and you get something unhelpful. 

book = Book("Dune", 3)
print(book)          # <__main__.Book object at 0x104f2c190>
print(book == book)  # True — but only because it is the same object

Two books with the same title are not equal, and printing one tells you nothing. Dunder methods fix both.

The failure Without dunders, your objects do not participate in the language. You cannot print them, compare them, or use them in loops the way you expect.

2Plug into the syntax

Each dunder maps to a piece of syntax. Define the method, and the syntax starts working.

Key idea Dunders are the hooks between your class and Python's syntax. You are not inventing new syntax — you are teaching Python how your object behaves in the syntax it already has.

3__str__ and __eq__

These two are the ones you will write most often. __str__ controls printing; __eq__ controls equality. 

class Book:
    def __init__(self, title, copies):
        self.title = title
        self.copies = copies

    def __str__(self):
        return f"Book({self.title!r}, copies={self.copies})"

    def __eq__(self, other):
        if not isinstance(other, Book):
            return NotImplemented
        return self.title == other.title

print(Book("Dune", 3))                       # Book('Dune', copies=3)
print(Book("Dune", 3) == Book("Dune", 9))    # True
Two rules Return NotImplemented (not False) when the other object is a different type. And if you define __eq__, define __hash__ too if the object should be usable in sets or as dict keys.
