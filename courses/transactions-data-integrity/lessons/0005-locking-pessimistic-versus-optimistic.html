Lesson 05 · Locking & Concurrency Control

Locking: pessimistic versus optimistic

How do you prevent two users from booking the exact same seat? Compare pessimistic locking (SELECT FOR UPDATE) with optimistic locking (version columns).

Time ~10 min Win Implement pessimistic and optimistic locking strategies to eliminate lost updates Mission link Prevents race conditions in ticketing, inventory, and balance systems

1The lost update problem

Two users click 'Buy' on the last concert seat at the exact same second. Both transactions read available = true. Both proceed to charge the card. Both write available = false. The seat was sold twice! This is a Lost Update anomaly.

You can prevent this using Pessimistic Locking (SELECT ... FOR UPDATE locks the row immediately until transaction commit) or Optimistic Locking (checking a version column at write time: UPDATE ... WHERE id = 1 AND version = 3).

Key idea Use pessimistic locking for high-contention writes; use optimistic locking for low-contention reads.

2Pessimistic versus Optimistic comparison

Evaluate the trade-offs between locking upfront versus checking versions on commit.

3Tracing optimistic lock conflict detection

Trace how a version column detects concurrent edits and rejects the second writer cleanly.
