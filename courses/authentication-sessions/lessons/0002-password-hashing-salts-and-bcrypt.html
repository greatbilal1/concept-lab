Lesson 02 · Identity & Password Security

Password hashing, salts, and bcrypt

Never store plaintext passwords. Learn why MD5 and SHA-256 are dangerous for passwords, how random salts defeat rainbow tables, and why slow hashing with bcrypt is mandatory.

Time ~10 min Win Implement secure password hashing using bcrypt with adaptive work factors Mission link Prevents credential database breaches from exposing user passwords

1Why fast hashes are fatal for passwords

Storing passwords in plaintext is criminal negligence. But hashing them with fast algorithms like MD5 or SHA-256 is almost as bad: modern GPUs can compute billions of SHA-256 hashes per second, cracking short passwords in minutes via brute-force dictionary attacks.

Password hashing algorithms must be deliberately slow and memory-hard (like bcrypt or Argon2). Furthermore, every password must be combined with a unique, cryptographically random Salt before hashing to defeat precomputed rainbow table databases.

Key idea Password hashes must be slow, salted, and computationally expensive to resist GPU brute forcing.

2The role of the cryptographic salt

Observe how a unique random salt ensures two users with identical passwords have completely different hashes.

3Tracing bcrypt verification

Trace how bcrypt extracts the embedded salt from the stored hash to verify incoming login attempts.

4Practice

Test your recall of password storage principles.

✓ Your win for today

You can store user credentials securely using salted, slow adaptive hashing algorithms.

5Do this next

  1. Hash a test password using bcrypt.hashpw() with a cost factor of 12.
  2. Verify why two hashes of the same password produce completely different output strings.
  3. Benchmark how many milliseconds your server takes to compute one bcrypt hash.
