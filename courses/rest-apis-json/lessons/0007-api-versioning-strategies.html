Lesson 07 · Evolution & Documentation

API versioning strategies

APIs evolve, but you cannot break existing mobile apps and integrations. Compare URI path versioning, header versioning, and content negotiation.

Time ~10 min Win Design and implement API versioning strategies to manage breaking contract changes Mission link Ensures APIs can evolve features without breaking existing production clients

1The inevitability of breaking changes

A public API is a promise: once third-party clients write code against your endpoints, renaming a field or deleting an endpoint breaks their business. Adding a new optional field is safe (backward-compatible), but changing data types or removing fields is a breaking change.

When breaking changes are unavoidable, you must version your API. The three major strategies are URI Path Versioning (/v1/users), Custom Header Versioning (X-API-Version), and Content Negotiation (Accept: application/vnd.app.v1+json).

Key idea Add optional fields backward-compatibly; version the API only when breaking contracts.
