Lesson 05 · Data Warehouses & Orchestration

Data Warehouses, Data Lakes & Lakehouses

Understand the storage revolution: why columnar formats like Parquet outperform row-based databases for analytics by 100x.

Time ~10 min Win Contrast row vs columnar storage and explain the architecture of Data Lakes, Warehouses, and Lakehouses Mission link Select and optimize analytical storage engines to reduce query runtimes and cloud storage bills

1Row-oriented vs Column-oriented storage

Transactional databases (PostgreSQL, MySQL) store data by row: row 1 followed by row 2. This is optimal for OLTP: looking up a single user by primary key reads one contiguous block of disk.

Analytics queries do not look up single rows; they aggregate millions of rows across a few columns: SELECT region, SUM(revenue) FROM orders GROUP BY region. Reading row-oriented data forces the disk to scan every unused column (customer address, notes, email).

Columnar storage (e.g. Apache Parquet) stores all values of column A together, followed by column B. The query engine only reads the region and revenue bytes from disk, achieving 10–100x faster scans and superior compression.

Key idea Row storage is built for single-record lookups; columnar storage is built for aggregating millions of rows across few columns.

2The evolution: Warehouse vs Lake vs Lakehouse

Modern data architecture evolved through three generations:

  • Data Warehouse (Snowflake, BigQuery): Highly structured, proprietary columnar storage, blazingly fast SQL, managed security, higher cost.
  • Data Lake (AWS S3 + Parquet): Low-cost object storage holding raw, semi-structured files. Historically lacked ACID transactions.
  • Data Lakehouse (Delta Lake, Apache Iceberg): Brings ACID transactions, schema enforcement, and time travel directly to open Parquet files on object storage.
