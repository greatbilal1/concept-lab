Idempotency & Deduplication

If a nightly pipeline crashes halfway through, running it again must not create duplicate payments or skewed revenue numbers.

Time ~10 min Win Design idempotent pipeline tasks and write deduplicating upsert/merge queries Mission link Prevent double-counting revenue and corrupting business metrics during pipeline retries

1The principle of pipeline idempotency

In distributed data engineering, failure is inevitable. Servers run out of memory, network connections drop, and upstream APIs return HTTP 503. The standard response is to retry the failed job.

However, if your pipeline task simply executes INSERT INTO revenue SELECT * FROM staging, running the job twice doubles every sales record! An idempotent pipeline guarantees that running a task once, twice, or ten times on the same input produces the exact same final state.

Key idea An idempotent data pipeline can be safely retried after a failure without producing duplicate records or state corruption.

2Idempotent patterns: Overwrite and Merge

Two common strategies guarantee idempotency in data pipelines:

  • Delete-Insert / Overwrite: Partition by date (e.g. 2026-05-12). Before loading, wipe that partition or run INSERT OVERWRITE. Any retry cleanly replaces the partition.
  • Upsert (MERGE): Use a unique primary key (e.g. order_id). Match against existing rows: update if the timestamp is newer, insert if the ID is missing.
