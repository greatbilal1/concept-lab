Annotations at runtime

Annotations are not enforced — but they are not invisible either. They are stored, and frameworks read them to do real work.

Time ~12 min Win Read annotations as data Mission link Types that drive behaviour

1They are stored

Every annotation ends up in a dictionary on the object: 

def greet(name: str) -> str:
    return "Hi " + name

greet.__annotations__
# {'name': <class 'str'>, 'return': <class 'str'>}

Module-level and class-level annotations land in __annotations__ too. That is the whole mechanism frameworks build on.

2Forward references

A class cannot refer to itself by name inside its own body, because the name does not exist yet. The fix is to write the annotation as a string: 

class Node:
    def next(self) -> "Node":
        ...

The string is called a forward reference. It is resolved later, when something actually asks for the type.

3Resolving them

get_type_hints() resolves annotations, including forward references, into real objects:

And from __future__ import annotations makes every annotation a lazy string, which sidesteps most forward-reference problems and speeds up imports.

4Who reads them

Dataclasses use them to generate __init__. Pydantic uses them to validate input. FastAPI uses them to build request schemas and documentation. None of that would work if annotations vanished at runtime.

Key idea Annotations are stored as data in __annotations__. Frameworks read them to generate code, validate input and build docs.
