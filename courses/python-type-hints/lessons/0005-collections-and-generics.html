Lesson 05 · Generics

Collections and generics

A list is not just a list — it is a list of something. Generics let you say what, and that is where checking starts to pay off.

Time ~12 min Win Annotate any collection Mission link Types that carry their contents

1Collections take a parameter

Write the element type inside square brackets: 

names: list[str] = ["Ada", "Grace"]
ages: dict[str, int] = {"Ada": 36}
tags: set[str] = {"python", "typing"}
point: tuple[float, float] = (1.0, 2.0)

A bare list tells the checker nothing about the contents. A list[str] lets it catch names.append(42) immediately.

2Tuples are special

A tuple annotation lists one type per position, so a fixed-shape record is expressible: 

row: tuple[str, int, bool] = ("Ada", 36, True)
many: tuple[int, ...] = (1, 2, 3)

The ellipsis means "any number of this type". Use it when the length is not fixed but every element is the same type.

3TypeVar

Sometimes you need to say "these two positions must be the same type, whatever it is". That is what TypeVar is for: 

T = TypeVar("T")

def first(items: list[T]) -> T:
    return items[0]

Now first(["a"]) is a str and first([1]) is an int, and the checker tracks that relationship instead of falling back to Any.

4Why this matters

Generics are the difference between "a container" and "a container of the thing I expect". Almost every real bug that a checker catches in a large codebase is a mismatch between what a collection holds and what the code assumes it holds.

Key idea Always parameterise your collections. A bare list is a missed opportunity; list[str] is a promise the checker can enforce.
