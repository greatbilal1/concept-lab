Lesson 08 · Checking

Static checking with mypy

Annotations do nothing on their own. A checker is what turns them into feedback — and mypy is the one you will meet most often.

Time ~12 min Win Run a checker and read its output Mission link Feedback you can act on

1Running a checker

Install it, then point it at your code: 

pip install mypy
mypy src/

It reads your annotations, follows your imports, and prints one line per problem. Nothing runs — the analysis is entirely static.

2Reading the output

A typical error names the file, the line, the expected type and the actual one: 

src/app.py:12: error: Argument 1 to "greet" has
incompatible type "int"; expected "str"  [arg-type]

The bracketed code at the end is the error category. You can silence a specific category with a comment, but silencing should be rare and deliberate.

3Strictness

By default mypy is lenient: unannotated functions are treated as Any, so mistakes inside them go unnoticed. Strict mode refuses that bargain.

A common path is to start lenient, get the codebase annotated, then turn on strict flags one at a time. Turning everything on at once on a large codebase produces a wall of errors nobody fixes.

4Stubs

When a library has no annotations, a stub file (.pyi) supplies them without touching the library. Many popular packages ship stubs, and types-* packages exist for the rest.

Key idea A checker turns annotations into feedback. Start lenient, annotate, then tighten. Stubs let you type code you do not own.

5Check yourself

Answer from memory — do not scroll back up. Each option has the same number of words, so nothing gives the answer away.

✓ Your win for today

You can run mypy, read an error line, explain what strict mode changes, and say what a stub file is for.

6Do this next

  1. Run mypy on a small project and count the errors.
  2. Fix one error and re-run to confirm it disappeared.
  3. Turn on one strict flag and see what new errors appear.
