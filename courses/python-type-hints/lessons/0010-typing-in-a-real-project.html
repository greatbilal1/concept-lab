Lesson 10 · Together

Typing in a real project

Everything so far has been vocabulary. This lesson is about the decisions you make when you add types to a codebase that already exists.

Time ~14 min Win A plan for adopting types Mission link Intent that survives a team

1Start at the boundaries

Do not annotate everything at once. Start where data enters and leaves your program — public functions, API handlers, file readers. Those are the places where a wrong type causes the most damage and where annotations help readers most.

2Measure coverage

Type coverage is the proportion of your code that carries useful annotations. Tools can report it, and it makes progress visible: 

mypy --strict src/ | wc -l
# fewer lines each week is progress

A number that goes down over time is a far better motivator than a vague sense that the code is "getting typed".

3Where to stop

Not every line deserves an annotation. Local variables inside a short function are usually obvious. The value is at the edges: signatures, module constants, class attributes, and anything a caller can see.

Over-annotating has a cost too — noise, churn, and annotations that restate what the code already says. Aim for the smallest set of annotations that lets the checker catch real mistakes.

4Types as a team contract

The real payoff is social. An annotation is a promise to every future reader, and the checker is the referee. When a signature changes, the checker tells you every call site that needs updating — which is exactly the work you would otherwise do by grepping and hoping.

Key idea Annotate the boundaries first, measure coverage, and stop where the annotations stop catching real mistakes. Types are a contract, and the checker enforces it.
