Protocols and Callables

Not every type is a class you inherit from. Protocols describe shape, and Callable describes functions — both without touching the code they describe.

Time ~12 min Win Type duck-typed code Mission link Interfaces without inheritance

1Structural typing

Python has always been duck-typed: if it has the method, it works. Protocols give that idea a name the checker understands: 

class Sized(Protocol):
    def __len__(self) -> int: ...

def show(x: Sized) -> None:
    print(len(x))

Anything with a __len__ satisfies Sized — a list, a string, a dict. No inheritance required, and no change to those classes.

2Callable

Functions are values, and Callable types them. The brackets list the parameter types, then the return type: 

def apply(f: Callable[[int], str], n: int) -> str:
    return f(n)

Callable[[int], str] reads as "takes an int, returns a str". It is how you annotate callbacks, sort keys and decorators.

3Protocols in practice

Protocols shine at boundaries: a function that only needs .read() should not demand a full File. Annotating it with a protocol that has read lets callers pass a file, a socket, or a test double.

That is the payoff: your functions depend on the smallest shape they actually need, and the checker enforces it.

4Shape over lineage

Inheritance says "is a". Protocols say "behaves like". For most Python code the second is both more accurate and more flexible, because it does not force you to modify classes you do not own.

Key idea Protocols describe shape, not lineage. Callable[[A], B] types a function value. Both let you annotate code you cannot change.
