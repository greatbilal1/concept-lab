Programming & Computational Thinking — Cheat Sheet

The six moves, the definitions and the shapes, compressed onto one page. Print this, or keep it open while you work through the course.

1The six moves

See Lesson 01 — What computational thinking is

One loop, six moves
1. DECOMPOSE     one problem → many smaller ones
2. PATTERNS      which parts repeat or rhyme?
3. ABSTRACT      hide the detail behind a name
4. ALGORITHM     an ordered list a machine can run
5. EVALUATE      is it good, not just correct?
6. GENERALISE    what family does it solve?
        ↓
     test it → go round again

2Problem statement

See Lesson 01 — What computational thinking is

Three parts, written before you start
Given:   what you are handed (the input)
Produce: what must exist at the end (the output)
Rule:    what must be true of the output

Example
  Given:   a list of 40 names, unsorted
  Produce: the same names, in alphabetical order
  Rule:    every name appears once, in the right order

A wish cannot be tested. A statement can.

3Decomposition

See Lesson 02 — Decomposition

A good split covers everything, overlaps nothing
COVERS ALL WORK      nothing is left over
NO OVERLAP           no work done twice
PARTITION            both properties at once

Right size test
  can you say it in one sentence?
  could you hand it to someone else?

Dependencies
  choose dates ──▶ book flights
               ──▶ find a stay
  pack          (no arrows in = independent)

4Pattern recognition

See Lesson 03 — Pattern recognition

Two kinds of sameness
REPETITION   the same step, again and again
SIMILARITY   steps differing only in one value
             → one step with a hole in it

Three cases → one rule
  make coffee / toast / porridge
  prepare(food, seconds)   ← covers all three

Test it: hunt for a COUNTER-EXAMPLE
  a case that looks like it fits but does not
  → it shows where the pattern ends

5Abstraction

See Lesson 04 — Abstraction

A deal: use it without knowing the inside
INTERFACE       what it promises
                name · inputs · output
IMPLEMENTATION  how it actually does it

The interface is the contract.
Change the implementation freely —
as long as the promise still holds.

LEAKY ABSTRACTION
  forces you to know the insides anyway
  → move the abstraction, don't document the leak

Right level of detail = who is reading?

6Algorithms

See Lesson 05 — Algorithms

Four words, each doing work
FINITE        it ends — there is a last step
ORDERED       steps run in the order written
UNAMBIGUOUS   every step means exactly one thing
INPUT→OUTPUT  it turns what you have into what you need

Test: could a machine with no common sense
      follow this and get the right answer?

7Evaluation

See Lesson 06 — Evaluation

Correct is the lowest bar
CORRECTNESS   right output, every allowed input
              necessary — not sufficient

Four criteria
  EFFICIENCY   how much work it does
  CLARITY      can another person follow it?
  SIMPLICITY   fewest parts, fewest special cases
  CORRECTNESS  the floor, not the goal

Criteria pull against each other → TRADE-OFF

Compare, don't inspect
  "is this good?"      → opinion
  "is this better?"    → defensible

Stop when it meets the criteria well enough.
Refining forever is a way of never finishing.

8Generalisation

See Lesson 07 — Generalisation

One case → a whole family
Find the part that VARIES
  lift it out → a PARAMETER
  the fixed remainder = the general solution

  sort 40 names  →  sort(list, rule)

Know where the family ends
  the BOUNDARY is not a failure
  it is the edge of what you solved

Do not generalise too early
  one case does not show what varies
  wait for two or three real cases

The best generalisation is the METHOD
  the six moves, reused on any problem

9The three shapes

See Lesson 05 — Algorithms

Sequence, selection, iteration — that is all
SEQUENCE     step 1 → step 2 → step 3

SELECTION    if condition:
                 path A
             else:
                 path B

ITERATION    repeat until condition:
                 do the thing

Order is not decoration.
Same steps, different order → different result.

10Tracing

See Lesson 05 — Algorithms

Walk the steps by hand before you build
1. pick an input
2. walk the steps one at a time
3. write down the state after each step
4. if the state surprises you → you found a bug

Trace the EDGE CASES first
  empty · zero · the largest value
  algorithms fail at the edges

11Testing & going round again

See Lesson 08 — Putting it together

Finding a bug is the method working
TEST CASE   an input + the output you expect
EDGE CASE   an input at the boundary
CORRECTNESS right output for EVERY allowed input

Found a bug?
  fix the step
  trace the same case again
  → the loop closes, you go round

Do not throw the work away. Refine it.

12Common mistakes

See Lesson 01 · 02 · 03 · 04 · 05 · 06 · 07

The seven traps
1. A wish instead of a statement
   "sort the names" → says nothing testable

2. Splitting by time, not by work
   "the morning" still contains the whole problem

3. Forcing a pattern that needs exceptions
   a rule with three special cases is a coincidence

4. A leaky abstraction
   "don't call it twice or it jams" = it failed

5. Steps that assume the reader knows
   "add the usual amount" is a memory test

6. Judging by feeling, not by criteria
   "this feels cleaner" is a preference, not a test

7. Generalising from a single case
   you cannot see what varies from one example
