Lesson 08 · The loop

Putting it together

Six moves, one problem. This lesson takes a single task and runs it through the whole loop — decompose, find the pattern, abstract it, write the steps, evaluate the result, then generalise it.

Time ~14 min Win You can design a solution to a problem you have never seen Mission link This is the whole course in one worked example

1The problem

Here is a problem you have probably met. It is deliberately ordinary, because the point is the method, not the problem. 

Given:  a shelf of 60 books, in no particular order
Produce: the same books, arranged so that you can
         find any one of them quickly
Rule:   every book is on the shelf exactly once,
         and books are grouped by subject

Notice we started with a problem statement, exactly as Lesson 1 said. We know what we are given, what we must produce, and how we will check it. Now the loop begins.

2Move 1 — decompose

"Organise the shelf" is a fog. Cut it into parts that cover everything and overlap nothing: 

a. decide the subject groups
b. assign every book to a group
c. choose an order within each group
d. place the groups on the shelf
e. label the shelf so it can be found again

Five parts, no overlap, and together they cover the whole job. Now the dependencies: b needs a, c needs b, d needs c. Part e is independent — it can happen at any time.

3Move 2 — find the pattern

Look down the list for sameness. Parts b and c are the same shape: both take a pile of books and sort them into an order, differing only in what they sort by — subject in one case, title in the other. 

sort(books, by):
    for each book:
        work out its key using "by"
        place it in the right position
    return the sorted books

One rule now covers two parts. And it covers a third case we did not plan for: sorting by author, or by height, or by how recently you read it. That is the payoff from Lesson 3 — the rule is bigger than the problem.

4Move 3 — abstract

The rule needs an interface. What does a caller need to know? Only that you hand it books and a way of choosing a key, and you get back the same books in order. Everything else — how the key is computed, how positions are found — is hidden. 

Interface:      sort(books, by) → sorted books
Implementation: key computation, position finding,
                comparison, placement

Now the shelf organiser can use sort without knowing anything about how it works. And if we later make sort faster, nothing that uses it has to change. That is the deal from Lesson 4, kept.

5Move 4 — write the steps

Finally, the algorithm. Sequence, selection and iteration, in order: 

1. groups = decide the subject groups
2. for each book on the shelf:
3.     find the group whose subject matches
4.     add the book to that group
5. for each group:
6.     sort(group, by title)
7. place the groups on the shelf in order
8. label the shelf

Line 2 is iteration. Line 3 is selection — the book goes to whichever group matches. Line 6 is the abstracted rule from move 2, used twice over. Every step is something an executor could do without asking a question.

6Move 5 — evaluate it

Now trace it. Pick an edge case: a book whose subject is not in your groups. Walk the steps and watch what happens at line 3 — nothing matches, and the book is silently dropped. The rule says every book appears exactly once, so the algorithm is wrong.

That is correctness failing, and it is the first thing evaluation catches. But suppose you fix it and the algorithm now works. Evaluation still has a question left: is this solution good? Count the work. For 60 books you make 60 comparisons to place them, then sort each group — a few hundred steps in total. A solution that compared every book against every other book would need nearly two thousand. Same result, six times the work.

This is the loop closing. You do not throw the work away; you go round again with better information. Add a default group, or a step that reports the unmatched book. Then trace again.

Key idea Finding a bug by tracing is not a failure of the method — it is the method. The loop is designed to catch exactly this, cheaply, before anything is built.

7Move 6 — generalise it

The shelf is organised. Now the move that makes the work pay off twice: what family of problems did you just solve?

Look at what varied. The books were the input; the subject groups were the rule. Everything else — split into groups, sort within each group, place the groups in order — stayed the same. Lift out the parts that vary and you have organise(items, group_by, sort_by), which organises a shelf of books, a folder of files, a list of contacts, or a warehouse of parts.

And the boundary is clear too: this works for anything that can be grouped and sorted. It does not work for items with no group at all — that is where the family ends and a different solution begins.

Key idea You solved one problem and walked away with a solution to a whole class of them. That is the difference between doing the work and doing the work once.

✓ Your win for today

You took a problem you had never solved, ran it through all six moves, wrote a real algorithm, found a genuine bug by tracing it, judged the fix against a criterion, and generalised the result to a whole family of problems. That is the entire course, working end to end.

8Do this next

  1. Pick a problem from your own week and write its problem statement.
  2. Run it through all six moves, writing down each one.
  3. Trace your algorithm with one edge case and fix what you find.
  4. Name one other problem your solution would also solve.
