Lesson 04 · The core moves

Abstraction

A pattern gives you a rule. Abstraction decides what that rule shows to the outside world — and, more importantly, what it hides.

Time ~10 min Win You can name an abstraction and say what it hides Mission link Move 3 of six — it is what keeps a solution readable

1You already use abstractions all day

You drive a car without knowing how the fuel injection works. You use a kettle without knowing its wiring. In both cases you are relying on an abstraction: a simple outside that hides a complicated inside.

The outside is the interface — what it promises to do, what you give it, what you get back. The inside is the implementation — how it actually does it. The whole point is that you can use the first without knowing the second.

Key idea An abstraction is a deal: "you do not need to know how this works, only what it does." Every abstraction you build is a promise to keep that deal.

2Choosing what to hide

Abstraction is not about deleting detail — the detail still has to happen somewhere. It is about choosing which details the reader needs and moving the rest out of sight.

Take the breakfast rule from Lesson 3. Two people could read it: 

prepare(food, seconds)
    put food in container
    apply heat
    wait seconds
    take food out

Someone using the rule needs only the first line: give it food and a time, get breakfast. Someone fixing the rule needs the four steps inside. Same rule, two levels of detail — and the abstraction is what lets both readers exist at once.

3The interface is the contract

Once you have an interface, you can change the implementation freely, as long as the promise still holds. Swap the toaster for a grill and prepare(toast, 180) still means the same thing to everyone using it.

This is why abstractions are worth the effort: they let one part of a solution change without breaking the rest. The interface is the only thing the outside world is allowed to depend on.

Common mistake A leaky abstraction — one that forces you to know its insides anyway. If you have to remember "and don't call it twice in a row, or it jams", the abstraction has failed. The fix is to move the abstraction, not to document the leak.

4Abstraction is a choice, not a fact

There is no single correct abstraction for a problem. The right one depends on who is reading and what they need to do. A recipe for a beginner hides the chemistry; a recipe for a chef might expose it.

So the question is never "what is the true abstraction?" It is: who is reading this, and what can they safely not know? Answer that and the interface writes itself.

✓ Your win for today

You took a general rule and gave it an interface — a name, an input and an output — while deciding exactly which details to hide behind it. That is abstraction, and it is what makes a solution readable by someone else.

5Do this next

  1. Pick one everyday object and write its interface in one line.
  2. List three details that interface hides from you.
  3. Find one abstraction you use that leaks — where you must know the insides.
