Contracts: docstrings and hints

A function is a promise: give me these inputs, and I will give you that output. A docstring and a type hint write that promise down, so the next reader — often you, next week — does not have to guess.

Time ~10 min Win Write a function with a clear contract Mission link Make code readable

1A function is a contract

The contract of a function is what it needs and what it gives back. The name and parameters hint at it; the body decides it. But nothing in the code states it — unless you write it down. 

def area(width, height):
    return width * height

Is width in metres or pixels? Does it accept negative numbers? Does it round? The code does not say. A reader has to read the body and guess the intent — and guessing is where bugs come from.

2The docstring

A docstring is a string literal as the first line of a function body. It is not a comment — Python keeps it, and tools can show it. It is where the contract is written in plain language. 

def area(width, height):
    """Return the area of a rectangle.

    width and height are positive numbers in metres.
    """
    return width * height

Now the reader knows the units, the expectation, and the result — without reading the body. A good docstring says what the function does, not how it does it.

3The type hint

A type hint writes the contract in the signature itself: the expected type of each parameter, and of the return value. 

def area(width: float, height: float) -> float:
    """Return the area of a rectangle."""
    return width * height

Hints are not enforced at runtime — Python will still run the function with a string. Their value is for the reader and for tools: an editor can warn you before you run anything. The hint is documentation that a machine can check.

Key idea A docstring says what the function does in words. A type hint says what types go in and come out. Together they are the contract, written where the reader will look.
