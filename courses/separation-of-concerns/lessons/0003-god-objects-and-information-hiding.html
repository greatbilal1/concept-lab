Lesson 03 · Single Responsibility & Actors

God objects and information hiding

The monster class that knows everything and does everything. Learn how to slay the God Object antipattern and enforce David Parnas's Information Hiding principle.

Time ~10 min Win Slay God Objects by distributing responsibilities and encapsulating internal data structures Mission link Eliminates bloated monolithic classes that paralyze software maintenance

1The monster that ate your architecture

In decaying codebases, one class inevitably swells into a God Object (Blob): AppManager, SystemController, or UserDataContext. It has 4,000 lines of code, holds 40 properties, and contains 60 methods. Every other class in the application depends on it.

The cure is David Parnas's foundational principle of Information Hiding: Every module must hide a secret. That secret might be a database schema, an algorithm, or a formatting rule. External classes must interact only through narrow, public interfaces, with zero access to internal data structures.

Key idea A God Object knows and does too much; Information Hiding forces modules to encapsulate their secrets.

2God Object versus Modular Decomposition

Contrast the central bottleneck of a God Object with decentralized, cohesive modules.

3Tracing God Object refactoring

Trace how extracting cohesive secrets from a God Object breaks it down into small modules.

4Practice

Test your memory of information hiding principles.

✓ Your win for today

You can identify God Objects and systematically dismantle them using information hiding and module extraction.

5Do this next

  1. Find the largest class in your repository by line count using git or wc -l.
  2. Identify three distinct 'secrets' (e.g. file formats, third-party APIs) that class is failing to hide.
  3. Extract one secret into a standalone, encapsulated module with private internal state.
Primary source David Parnas: *On the Criteria To Be Used in Decomposing Systems into Modules* (Communications of the ACM, 1972).
