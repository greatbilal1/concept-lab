Lesson 04 · Single Responsibility & Actors

Presentation, domain, and persistence boundaries

Don't let your database leak into your HTML templates. Master the strict architectural boundaries between Presentation, Domain, and Persistence layers.

Time ~10 min Win Enforce strict boundary contracts between presentation views, domain entities, and database storage Mission link Prevents UI and database frameworks from corrupting core business policies

1The boundaries that protect the core

A software architecture is defined by the boundaries drawn through it. The two most critical boundaries in any web application are: 1. The Presentation Boundary (separates the web/UI from domain logic) and 2. The Persistence Boundary (separates domain logic from the database).

When these boundaries erode, chaos ensues: HTML templates execute SQL queries directly, and database models format currency symbols for web display. Crossing boundaries directly without Data Transfer Objects (DTOs) tightly couples the entire stack together.

Key idea Boundaries isolate layers: domain logic must never touch HTTP requests or raw SQL connections.

2Boundary crossing with DTOs

Observe how DTOs act as passports, translating data across layer boundaries safely.

3Tracing boundary enforcement in a controller

Trace how a controller respects boundaries by mapping HTTP requests into clean domain parameters.

4Practice

Test your memory of architectural boundaries.

✓ Your win for today

You can erect and defend architectural boundaries that prevent database and web framework churn from polluting domain logic.

5Do this next

  1. Audit your codebase to verify that no template or presentation file imports an SQL database connection.
  2. Ensure your domain entities return pure data rather than HTML-formatted strings.
  3. Define an explicit RequestDTO and ResponseDTO for a core API endpoint.
Primary source Robert C. Martin, *Clean Architecture*, Chapter 17: 'Boundaries: Drawing Lines'.
