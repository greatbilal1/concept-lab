Numbers that lie

Open a Python console and type 0.1 + 0.2. You will not get 0.3. This lesson explains why — and why it is not a bug, but a consequence of how the machine stores fractions.

Time ~12 min Win Run the float demo and explain it Mission link Why "obvious" code can be wrong

1The famous surprise

Run this in any language and you get the same strange answer: 

>>> 0.1 + 0.2
0.30000000000000004

Not 0.3. Off by a tiny amount, in the last digits. This is not a rounding bug in your language — Python, JavaScript, C and Java all do it. It is the IEEE 754 floating-point standard, and it is doing exactly what it was designed to do.

Key idea The machine stores fractions in binary. Some decimal fractions have no exact binary representation — just as $\frac{1}{3}$ has no exact decimal representation. The error is unavoidable, not accidental.

2Why 0.1 cannot be stored

In decimal, $\frac{1}{3} = 0.3333\ldots$ forever. You cannot write it exactly, so you write 0.333 and accept a small error.

In binary, $\frac{1}{10}$ has the same problem. Its binary expansion is 0.0001100110011... repeating forever. A fixed number of bits cannot hold it, so the machine stores the nearest value it can — and that value is slightly off. 

0.1  →  0.1000000000000000055511151231257827...
0.2  →  0.2000000000000000111022302462515654...
sum  →  0.3000000000000000444089209850062616...

Add the two stored values and the errors accumulate into that trailing 4.

3How a float is laid out

A 64-bit float is not one number — it is three fields packed together: 

1 bit   sign      0 = positive, 1 = negative
11 bits exponent  the scale (power of two)
52 bits fraction  the significant digits

This is scientific notation in binary: sign × fraction × 2^exponent. The fraction field gives you about 15–17 significant decimal digits, which is why the error shows up so far to the right.

The rule that follows Never compare floats with ==. Compare the difference against a small tolerance instead. And never use floats for money — use integers of cents, or a decimal type.

4Run the demo

Here is the win. Run these in a Python console and predict each result first: 

>>> 0.1 + 0.2
>>> 0.1 + 0.2 == 0.3
>>> round(0.1 + 0.2, 2) == 0.3
>>> 1e16 + 1 == 1e16

The first gives the long tail. The second is False — the classic trap. The third is True, because rounding cleans it up. The fourth is True as well: at that magnitude, adding 1 changes nothing, because the fraction field cannot represent the difference.

✓ Your win for today

You can now explain the most famous "bug" in programming, describe how a float is laid out, and state the two rules that follow: never compare floats for equality, and never store money in them. You have also learned the deeper lesson — a data type is a promise with limits, and knowing the limits is what separates guessing from engineering.

6Do this next

  1. Run 0.1 + 0.2 in your language of choice. Then run 0.1 + 0.2 - 0.3 and look at the result.
  2. Work out why 1e16 + 1 == 1e16 is true. How many bits would you need to tell those two numbers apart?
  3. Find a place in your own code where you compare two floats with ==. Rewrite it to use a tolerance.
