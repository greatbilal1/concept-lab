# Mission established: understand the machine under the code

The user's reason for learning this is **to stop treating the computer as a magic
box**. They already write code; what they lack is the layer underneath — what
actually happens when a line runs. This grounds every lesson in *explaining
observed behaviour* (why is this slow, why is this number wrong, where did this
value go) rather than in hardware trivia.

## Implications
- Lessons should end with something **counted, built, or run** — never just read.
- No hardware required: everything must be demonstrable in a browser or terminal.
- Numbers (binary, hex) come first because every later lesson depends on them.
- Prefer *reading* assembly over *writing* it; the goal is comprehension.
- Out of scope for now: OS internals, GPU, networking, electronics lab work.

## Evidence
Stated directly by the user when the course was requested: "How computers actually
work", planned as a foundations course in the Concept Lab catalogue, to be built in
the same style and structure as the existing OOP course. The user asked explicitly
that it follow "the reusable stuff we set in the code base" — i.e. content only,
shared components, no forked assets.
