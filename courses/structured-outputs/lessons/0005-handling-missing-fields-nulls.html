Handling Missing Fields, Nulls, and Schema Mismatches

Handling the messy reality of data: optional attributes, nullable fields, default values, and schema mismatch defenses.

1Core principles of Handling Missing Fields, Nulls, and Schema Mismatches

A critical trap in structured output engineering is Over-Constraining Required Fields. If you tell an LLM that phone_number: str is strictly required, and you feed it an email that contains no phone number, what will the model do?

Key idea Handling the messy reality of data: optional attributes, nullable fields, default values, and schema mismatch defenses.

2Required vs Nullable Fields

Because the schema grammar forces it to emit a string, the model will hallucinate a fake phone number (e.g. "555-0199") just to satisfy your schema!

3Default Collections Pattern

To prevent hallucinated data, author schemas with defensive nullability:

  • 1. Explicit Nullable Types: Use `str | None = None` in Python or `z.string().nullable()` in TypeScript for any attribute that might be missing in real documents.
  • 2. Explicit Sentinel Explanations: Add field descriptions guiding the model: 'Phone number if present in document, otherwise null.'
  • 3. Sensible Defaults: Use default values for collections: `tags: list[str] = Field(default_factory=list)`. An empty list `[]` is vastly cleaner to handle downstream than `null`.
# Defensive Schema Design (Preventing Hallucinations):
class ContactDetails(BaseModel):
    name: str = Field(description="Full name of the contact person")
    # Nullable fields: Model outputs null instead of inventing fake data!
    phone: str | None = Field(default=None, description="Phone number if present, else null")
    department: str | None = Field(default=None, description="Department if stated, else null")
    notes: list[str] = Field(default_factory=list, description="Extracted notes (empty if none)")

The Honesty Law: Allowing fields to be `null` gives the model the mathematical freedom to be honest when information is absent.
