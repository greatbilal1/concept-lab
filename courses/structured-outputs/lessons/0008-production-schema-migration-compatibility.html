Production Schema Migration and Backward Compatibility

Evolving schemas in production: adding fields safely, backward compatibility, versioning, and deprecation cycles.

Time ~10 min Win You have completed the Structured Outputs & JSON course. Mission link Mastering production schema migration and backward compatibility across modern software engineering

1Core principles of Production Schema Migration and Backward Compatibility

Software is never static. As products evolve, schemas change: you add a discount_code field, split full_name into first_name and last_name, or introduce a new status enum. In an AI application, modifying a schema touches prompt templates, model outputs, cached records, and database rows.

Key idea Evolving schemas in production: adding fields safely, backward compatibility, versioning, and deprecation cycles.

2Backward-Compatible Schema Migration

To manage Schema Evolution without Breaking Production:

3The Missing Default Trap

  • 1. The Additive Default Rule: When adding a new field to an existing schema, always provide a default value: `discount_code: str | None = None`. This ensures that historical JSON objects stored in your database can still be deserialized cleanly!
  • 2. Schema Versioning: Name or tag schemas with explicit version identifiers: `InvoiceSchemaV1`, `InvoiceSchemaV2`. This allows you to run parallel endpoints during migrations.
  • 3. Two-Phase Migrations: Phase 1: Deploy code that can parse both V1 and V2 formats. Phase 2: Update the prompt to generate V2. Phase 3: Deprecate V1 after all cached responses have expired.
# Backward-Compatible Schema Evolution (Pydantic v2):
class UserProfileV2(BaseModel):
    user_id: str
    email: EmailStr
    # NEW FIELD: Has default value, ensuring V1 records parse without errors!
    tier: Literal["free", "pro", "enterprise"] = "free"
    # DEPRECATED FIELD: Kept as optional for backward compatibility with old records
    legacy_notes: str | None = None
