Lesson 02 · Layers & Architectural Boundaries

The Dependency Rule and Clean Architecture

High-level policy should not depend on low-level details. Master Robert C. Martin's Dependency Rule: why dependencies must strictly point inward toward business entities.

Time ~10 min Win Apply the Dependency Rule to protect business entities from database and UI framework changes Mission link The core design principle of Clean Architecture and Onion Architecture

1The inverted dependency flow

In traditional layered architectures, business logic depends on the database: if you change your ORM, your business services break. Robert C. Martin's Clean Architecture inverts this.

At the center of Clean Architecture sit Entities and Use Cases. At the outer edge sit Frameworks, Web Servers, and Databases. The central Dependency Rule states: Source code dependencies must point strictly INWARD. Nothing in an inner circle can know anything about an outer circle.

Key idea Source code dependencies must point inward: business rules never depend on databases or frameworks.

2The concentric circles of Clean Architecture

Observe how business logic is protected from outer technology churn.

3Tracing the inward dependency path

Trace how dependency inversion allows high-level use cases to command repositories via interfaces.

4Practice

Test your memory of Clean Architecture principles.

✓ Your win for today

You can design systems where business logic remains pristine and testable, completely decoupled from database libraries.

5Do this next

  1. Audit a business entity to ensure it contains zero ORM or framework imports.
  2. Define an interface for a database repository inside your domain package.
  3. Implement an in-memory mock repository to run fast unit tests without a database.
Primary source Robert C. Martin, *Clean Architecture: A Craftsman's Guide to Software Structure and Design* (Prentice Hall, 2017).
