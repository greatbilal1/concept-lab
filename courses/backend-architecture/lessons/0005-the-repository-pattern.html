Lesson 05 · Services & Repositories

The repository pattern

Isolate your database behind a clean in-memory collection facade. Discover the Repository pattern: why domain logic should never write SQL, and how to build testable repositories.

Time ~10 min Win Implement the Repository pattern to decouple domain services from database technologies Mission link The standard persistence abstraction layer in enterprise backend systems

1A collection-like interface to data

If every service writes raw SQL queries, changing database columns or optimizing queries requires editing dozens of business files. The Repository Pattern encapsulates data access behind a collection-like facade.

To the business service, the repository looks like a simple in-memory list: repo.get_by_id(42), repo.save(user), repo.find_active(). All SQL queries, ORM sessions, and database drivers are completely encapsulated inside the repository implementation.

Key idea A repository presents a collection-like interface to the domain, hiding all database mechanics.

2Repository abstraction architecture

Observe how the domain service interacts with a pure interface rather than a database.

3Tracing the swap to a MockRepository in testing

Trace how the repository pattern allows running unit tests in 2 milliseconds with an in-memory dictionary.

4Practice

Test your memory of the Repository pattern.

✓ Your win for today

You can implement clean Repository interfaces that encapsulate all data access and enable blazing-fast testing.

5Do this next

  2. Implement an SQLAlchemy or Prisma repository that fulfills that interface.
  3. Write a unit test for your service using a dictionary-backed in-memory repository.
