Lesson 07 · Configuration & Observability

Configuration boundaries and Twelve-Factor apps

Never hardcode configuration. Master Factor III of the Twelve-Factor App: managing environment variables, secrets management, and circuit breakers for resilience.

Time ~10 min Win Implement validated configuration boundaries using environment variables and Pydantic Mission link Prevents credential leaks and configuration drift across staging and production

1Code is static; configuration varies

A production-grade backend codebase is compiled or built once, and deployed identically across multiple environments: local development, continuous integration, staging, and production. What changes between these environments?

Configuration: database URLs, API credentials, cache hostnames, and logging levels. Following Factor III of the Twelve-Factor App, all configuration that varies across deploys must be injected via environment variables, never hardcoded in source files.

Key idea Build one immutable artifact; inject environment-specific configuration via environment variables.

2The configuration validation boundary

Observe how a strongly-typed settings object parses and validates environment variables on boot.

3Tracing circuit breaker protection

Trace how a circuit breaker halts requests to a failing third-party API to prevent cascading thread exhaustion.

4Practice

Test your memory of backend configuration rules.

✓ Your win for today

You can design fail-fast configuration boundaries and implement circuit breakers to guard against downstream service outages.

5Do this next

  1. Create a validated Settings class using pydantic-settings in Python or Zod in TypeScript.
  2. Verify that your app refuses to start if a required database URL is omitted.
  3. Implement a simple circuit breaker state machine around an external HTTP API client.
