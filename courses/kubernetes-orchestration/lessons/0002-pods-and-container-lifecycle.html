Pods & Container Lifecycle Management

You do not run containers directly in Kubernetes; you run Pods. Understand why containers share localhost and volumes.

Time ~10 min Win Write Pod manifests, use multi-container patterns (sidecars), and diagnose container lifecycle states Mission link Diagnose CrashLoopBackOff, OOMKilled, and image pull failures rapidly

1Why Pods instead of bare containers?

A Pod is the atomic unit of scheduling in Kubernetes. While most pods contain just one container, a pod can host multiple tightly coupled containers that share:

  • Network namespace: All containers in a pod share the same IP address and port space; they communicate with each other over localhost.
  • Storage volumes: Containers in the same pod can mount shared volumes to exchange files.
  • IPC namespace: Shared POSIX shared memory or signals.
Key idea Containers in the same pod share an IP address and communicate with each other over localhost.

2Init containers and sidecars

Pods support two important architectural patterns:

  • Init Containers: Run sequentially to completion before app containers start (ideal for database migrations, waiting for dependencies, or fetching secrets).
  • Sidecar Containers: Run in parallel alongside the main application to handle cross-cutting concerns like log shipping (Fluentd) or proxying (Envoy / Istio).
