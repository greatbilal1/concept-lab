Deployments, ReplicaSets & Rolling Updates

Never create standalone Pods in production. Deployments manage ReplicaSets to ensure high availability and zero-downtime rollouts.

Time ~10 min Win Manage stateless applications using Deployments, execute rolling updates, and perform instant rollbacks Mission link Ship code changes to production continuously without dropping a single active customer request

1The Deployment hierarchy

If you create a naked Pod and its worker node crashes, that pod is dead forever. To achieve high availability and self-healing, Kubernetes provides controller hierarchies:

  • Deployment: High-level controller representing your application version. Handles updates and rollbacks.
  • ReplicaSet: Mid-level controller managed by the Deployment that guarantees an exact number of identical pod replicas are running.
  • Pod: The running workload instances.
Key idea A Deployment manages ReplicaSets; a ReplicaSet manages Pods. Never modify ReplicaSets directly.

2Rolling update parameters: maxSurge and maxUnavailable

You fine-tune rolling update behavior using two properties:

  • maxSurge: How many extra pods can be created above the desired replica count during the rollout (e.g. 25%).
  • maxUnavailable: How many pods can be unavailable during the update process (e.g. 0 guarantees no capacity loss).
