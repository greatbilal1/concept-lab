Lesson 05 · Networking, Services & Ingress

Services, ClusterIP, NodePort & kube-proxy

Pods are ephemeral and their IP addresses change constantly. Services provide stable virtual IPs and load balancing.

Time ~10 min Win Create ClusterIP, NodePort, and LoadBalancer services and explain kube-proxy packet routing Mission link Provide dependable internal and external network routing across dynamic container fleets

1The problem of ephemeral Pod IPs

Every pod in Kubernetes gets a private IP address. But pods crash, scale up, and roll over constantly—each new pod receives a new IP address. If frontend pods hardcoded backend pod IPs, everything would break within minutes.

A Service is an abstraction that defines a logical set of Pods (identified by a label selector) and a policy by which to access them. A Service gets a permanent, stable virtual IP (ClusterIP) and a DNS name (e.g. api-service.default.svc.cluster.local) that never changes.

Key idea A Service provides a permanent virtual IP and DNS name that routes traffic across dynamically changing Pod IPs.

2The four Service types

Kubernetes provides four Service exposure types:

  • ClusterIP (Default): Exposes the Service on an internal cluster-only virtual IP. Accessible only from inside the cluster.
  • NodePort: Exposes the Service on a static high-range port (30000–32767) on every worker node's external IP.
  • LoadBalancer: Provisions an external cloud load balancer (e.g. AWS NLB, GCP Load Balancer) that routes to the Service.
  • ExternalName: Maps the Service to a CNAME DNS record outside the cluster.
