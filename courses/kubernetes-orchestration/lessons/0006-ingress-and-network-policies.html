Lesson 06 · Networking, Services & Ingress

Ingress Controllers & Network Security Policies

Creating a cloud LoadBalancer for every microservice is costly and wasteful. Ingress consolidates traffic behind a single smart reverse proxy.

Time ~10 min Win Configure Ingress rules for path-based routing and secure inter-pod communication with NetworkPolicies Mission link Save cloud infrastructure costs and implement zero-trust network boundaries across microservices

1Ingress: One entry point for the cluster

If your company operates 20 microservices, creating 20 type: LoadBalancer services incurs 20 separate cloud load balancer bills (hundreds of dollars a month). More importantly, basic cloud load balancers cannot inspect HTTP host headers or URL paths.

An Ingress object manages external HTTP and HTTPS access to cluster services. An Ingress Controller (such as NGINX Ingress, Traefik, or Envoy) runs as a reverse proxy, inspecting hostnames (e.g. api.example.com vs app.example.com) and paths (/users vs /orders) to route traffic using a single cloud IP address.

Key idea Ingress consolidates external HTTP/HTTPS routing, TLS termination, and path-based routing behind a single entry point.

2Zero-trust with NetworkPolicies

By default, Kubernetes uses a flat, open network: any Pod in any namespace can communicate with any other Pod in the cluster. If an attacker compromises a public web pod, they can query internal database pods unrestricted.

A NetworkPolicy functions as a distributed firewall. You specify ingress (incoming) and egress (outgoing) rules using label selectors, locking down communication to only authorized services.
