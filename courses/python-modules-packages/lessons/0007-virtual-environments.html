Lesson 07 · Environments

Virtual environments

Two projects need two different versions of the same library. Without environments that is impossible, and the failure is silent until it is not. This lesson is about the one directory that fixes it.

Time ~10 min Win Isolate a project's dependencies Mission link Reproducibility is a feature

1The version collision

Project A needs requests 2.28. Project B needs requests 2.32. If both install into the same interpreter, one of them is wrong — and whichever installed last wins. The other project breaks, often in a way that looks like a bug in your code.

A virtual environment solves this by giving each project its own site-packages directory. Installing into one environment cannot touch another, because they are different folders on disk.

2What is actually inside one

A virtual environment is not a copy of Python. It is a small directory holding a link to the interpreter, its own package folder, and a few scripts that activate it.

Because the interpreter is shared and only the packages are separate, creating an environment is fast — a second or two, not a reinstall of Python.

Key idea An environment isolates packages, not the interpreter. That is why it is cheap, and why it is the right tool for per-project dependency sets.

3Create, activate, verify

The workflow is three commands, and the third one is the one people skip: 

python -m venv .venv          # create
source .venv/bin/activate     # activate (macOS / Linux)
# .venv\Scripts\activate      # activate (Windows)

which python                  # verify: should point inside .venv
pip install requests          # installs into THIS environment only

That which python check is worth making a habit. If it does not print a path containing .venv, you are about to install into the wrong place.

4Activation is just PATH editing

"Activating" sounds like magic. It is not. The activate script prepends the environment's bin directory to your shell's PATH, so that python and pip resolve to the environment's copies first.

That is why activation is per-shell: a new terminal does not inherit it. And it is why deactivate is just a function that puts the old PATH back.

Why this matters later Every deployment, every CI pipeline, every Dockerfile you will ever write creates an environment and installs into it. The commands change slightly; the concept is exactly this one. Get it right locally and the rest is translation.

✓ Your win for today

You can now create an isolated environment, verify you are inside it, and explain what activation actually does to your shell. No more "it works on my machine" caused by a shared package folder.

6Do this next

  1. Create a .venv in a scratch folder, activate it, and run which python. Then deactivate and run it again.
  2. Install any small package inside the environment, then deactivate and try to import it. Confirm it is gone from the global interpreter.
  3. Add .venv/ to a .gitignore. Environments are rebuilt, never committed.
