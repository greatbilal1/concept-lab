Three ways to import

Python gives you three spellings for the same operation, and they are not interchangeable. Each one binds a different name in your file, and choosing badly is how codebases end up with names nobody can trace.

Time ~10 min Win Pick the right import form Mission link Readable names are a design decision

1Same operation, three bindings

Every import does the same work underneath: find the file, run it once, cache it. What differs is what name lands in your namespace. That is the only question that matters when you choose a form.

Read those three lines again and notice the difference. The first binds helpers. The second binds with_tax. The third binds h. Three different names, one module.

2Plain import: the default

import helpers is the form you should reach for first. It binds the module object, and every use is prefixed with the module name: 

import helpers

helpers.with_tax(50)
helpers.TAX_RATE

The prefix looks like extra typing. It is not — it is provenance. Six months from now, helpers.with_tax tells you exactly where the function came from. A bare with_tax tells you nothing.

Key idea Prefer the form that keeps the origin visible at the call site. Plain import does that by default, which is why it is the safe choice.

3from-import: bind the name directly

from helpers import with_tax skips the module object and binds the function itself. Now you call with_tax(50) with no prefix.

This is genuinely useful when the module name adds nothing — from math import sqrt reads better than math.sqrt in a formula. But it has a cost: the name in your file no longer says where it came from, and it can be shadowed by anything else you define.

4Aliases: rename on the way in

import helpers as h binds the module under a new name. Aliases exist for two honest reasons: the real name is long, or the real name collides. 

import numpy as np
import pandas as pd
from myapp.very.long.path import config as cfg

The first two are community conventions — everyone writes np and pd, so using anything else is a small act of hostility. The third is a local decision: shorten a path that would otherwise dominate every line.

Why this matters later When you read someone else's code, the import block is the map. Plain imports tell you which modules are in play; from-imports tell you which names were pulled in; aliases tell you what the author decided to abbreviate. Learn to read that block and you can orient in any codebase in a minute.

✓ Your win for today

You can now read any import block and say exactly which names it created, and you can choose a form deliberately instead of by habit. That is the difference between code that is merely working and code that is legible.

6Do this next

  1. Take yesterday's split script and rewrite the import all three ways. Run it each time and confirm the output is identical.
  2. Find a from-import in your own code where the module name would have added clarity. Change it to a plain import and see if the call sites read better.
  3. Look up the import block of a library you use. Count how many aliases it uses and guess why each one exists.
