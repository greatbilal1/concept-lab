Import traps and how to escape them

Three failures account for almost every confusing import bug you will ever hit. Each one has a name, a cause, and a fix — and once you can name them, they stop being mysterious.

Time ~10 min Win Name and fix three traps Mission link Debugging beats guessing

1Trap one: the circular import

Module A imports B, and B imports A. Python starts loading A, hits the import of B, starts loading B, which hits the import of A — and A is only half-built. The name B needs may not exist yet. 

# a.py
import b
def helper(): return b.value

# b.py
import a
value = a.helper()   # ImportError: partially initialised

The fix is almost never "add more imports". It is to break the cycle: move the shared piece into a third module both can import, or import inside the function that needs it so the load happens later.

2Trap two: shadowing

You create json.py next to your script. Now import json finds your file first, because the script's directory is at the front of sys.path. The standard library loses silently.

The symptom is bizarre: a library that worked yesterday now raises AttributeError: module 'json' has no attribute 'dumps'. The cause is a filename. Rename the file and the error vanishes.

Key idea Never name a file after a module you import. The classic offenders are json.py, random.py, types.py, email.py and logging.py.

3Trap three: the star import

from helpers import * dumps every public name from the module into your namespace. It looks convenient and it destroys traceability. 

from helpers import *

clean(rows)   # where did clean come from? no idea.

Worse, a star import can silently overwrite a name you already had. If helpers defines clean and so do you, the import wins and your function disappears with no warning.

4The escape pattern

All three traps share one root cause: the origin of a name is not visible. The fix is the same in every case — make the origin explicit.

Name the module, name the symbol, and keep the dependency graph acyclic. That is the whole discipline, and it is why the earlier lessons pushed plain imports so hard.

Why this matters later These three traps are the ones that cost real hours. A circular import in a large codebase can take a day to untangle; a shadowed module can look like a broken library. Recognising the shape of the failure is most of the fix.
