Lesson 05 · Packages

Relative vs absolute imports

Inside a package you can name a sibling module two ways: from the project root, or from where you are standing. Both work. Only one of them survives a refactor, and this lesson is about which.

Time ~10 min Win Choose imports that survive moves Mission link Write code that is easy to change

1Two ways to say the same thing

Suppose you are editing myapp/report.py and you need clean from myapp/helpers.py. You have two spellings: 

# absolute — from the project root
from myapp.helpers import clean

# relative — from where this file sits
from .helpers import clean

The leading dot in the second one means "the package I am in". Two dots mean "the parent package". The name is resolved relative to the file's own location, not to the directory you ran Python from.

2Reading the dots

The dot count is a small grammar, and it is worth memorising exactly:

Notice that a relative import can never escape the top-level package. There is no syntax for "go above the root", which is deliberate — it keeps a package self-contained.

Key idea A relative import says "near me". An absolute import says "from the root". Only the absolute one still means the same thing if you move the file.

3The refactor test

Here is the argument that settles it. Imagine you decide report.py belongs in a new subpackage, so you move it from myapp/report.py to myapp/output/report.py.

The absolute import kept working because it never mentioned the file's own location. The relative import broke, because .helpers now means myapp.output.helpers, which does not exist. That is the whole trade-off in one move.

4So when is relative right?

Relative imports are not wrong — they are local. They are a good fit when the package is a self-contained unit that will be vendored, copied, or renamed as a whole, because then "near me" is exactly the relationship you mean.

The practical rule most teams settle on: absolute imports by default, relative imports only for short hops within a tightly coupled subpackage. And never mix the two styles for the same relationship in the same file.

Why this matters later Import style is the first thing a reviewer notices. Absolute imports make a file readable in isolation — you can open it, see from myapp.helpers import clean, and know where to look without knowing where the file lives. That property is worth more than the few characters you save.

✓ Your win for today

You can now read any import and say whether it is anchored to the root or to the file, and you can predict which ones break when a file moves. That is a refactoring skill, not just a syntax fact.

6Do this next

  1. In a package you own, find every relative import. For each one, ask whether moving that file would break it.
  2. Convert one relative import to absolute and run the code. Then move the file into a subpackage and confirm the absolute one still works.
  3. Try from .. import something from a top-level module and read the error. It is the "attempted relative import beyond top-level package" message.
