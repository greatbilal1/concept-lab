Lesson 05 · Race Conditions & Sequencing

Race conditions and request sequencing

Fast typing breaks slow APIs. Discover why rapid search queries can return out of order, and how to fix race conditions using AbortController and debouncing.

Time ~10 min Win Prevent out-of-order search autocomplete bugs using debouncing and AbortController Mission link Eliminates subtle asynchronous bugs where stale network data overwrites fresh data

1The out-of-order response trap

Imagine a search input. The user types 'cat', triggering Request A. Then they type 's' ('cats'), triggering Request B. Request B is sent after Request A, but due to network routing, Request B finishes in 50ms, while Request A takes 300ms.

What happens? Request B renders results for 'cats'. Then 250ms later, Request A finally arrives and overwrites the screen with results for 'cat'! The user typed 'cats', but sees results for 'cat'. This is a classic network race condition.

Key idea Later requests can arrive before earlier requests; always cancel or discard stale in-flight responses.

2Debouncing versus cancellation

Combine debouncing (delaying request firing) with AbortController (cancelling active requests).
