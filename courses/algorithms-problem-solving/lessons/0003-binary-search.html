Lesson 03 · Searching

Binary search

Linear search checks every item. Binary search throws away half the list on every single step — but only if the list is sorted first. That one precondition is the whole story.

Time ~12 min Win Halve a search space by hand and count the steps Mission link The first algorithm that beats the obvious one

1Guess the number, but smart

Think of the game where someone picks a number between 1 and 100 and you have to guess it. If you guess 1, then 2, then 3, you are doing linear search — and you might need 100 guesses. If instead you guess 50, and they say "too low", you have just eliminated half the numbers in one guess.

That is binary search. Look at the middle. If it is too small, the answer must be to the right, so throw away the left half. If it is too big, throw away the right half. Repeat on what is left.

Key idea Binary search works by halving the search space every step. 100 items take at most 7 steps; a million items take at most 20.

2The precondition you cannot skip

Here is the catch, and it is the single most common bug in this algorithm: binary search only works on a sorted list. If the data is not in order, "too low" tells you nothing about where the answer is, and halving the range throws away the item you were looking for.

So the honest cost of binary search is not just the search — it is the search plus the sort you had to do first. That trade-off is the subject of lesson 8.

Watch out Run binary search on an unsorted list and it will not crash — it will quietly return the wrong answer. Silent wrongness is worse than an error.

3Halve it by hand

Search for 23 in the sorted list [4, 8, 15, 16, 23, 42, 99]. Watch the range shrink each step.

Seven items, three comparisons. Linear search would have needed five. On a list of $n$ items binary search needs about $\log_2 n$ comparisons — the number of times you can halve $n$ before reaching one.

✓ Your win for today

You can run binary search by hand on a sorted list, say why the sorted precondition is non-negotiable, and explain why the cost is about $\log_2 n$ rather than $n$.

5Do this next

  1. Write binary search in pseudocode with low and high bounds. Decide what happens when the target is absent.
  2. Trace it on [1, 2, 3, 4, 5, 6, 7, 8] looking for 8. How many comparisons? Now try 1. Why are they different?
  3. Deliberately run it on an unsorted list and find an input where it returns the wrong answer. Seeing the failure makes the precondition stick.
Primary source Read _Introduction to Algorithms_ by Cormen, Leiserson, Rivest & Stein, Chapter 2, Section 2.3 ("Designing algorithms") for the divide-and-conquer framing, then the binary-search exercise in Chapter 2's problems.
