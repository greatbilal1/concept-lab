What an algorithm really is

You already follow algorithms all day — a recipe, a bus route, the way you find a word in a dictionary. This lesson names the thing you have been doing, and gives you the two habits that make it reliable: decomposition and tracing.

Time ~10 min Win Write an algorithm precise enough to follow blindly Mission link The habit every later lesson depends on

1A recipe is not an algorithm yet

"Add some flour and bake until done" is a recipe. It is not an algorithm, because two people following it will produce two different cakes. An algorithm is a sequence of steps that is finite, unambiguous, and guaranteed to stop. Follow it exactly and you get the same answer every time, no judgement required.

That last part is the whole point. A computer cannot guess what "some flour" means. Every step has to be something a machine can do without understanding anything.

Key idea An algorithm is not code. It is the idea — the steps — and code is just one way of writing that idea down. The same algorithm can be written in Python, in JavaScript, or on paper.

2Write it in pseudocode first

Before you write code, write pseudocode: plain language, one step per line, indented to show what repeats. It has no syntax to argue about, so you can check the logic while it is still cheap to change.

3Trace it before you trust it

A trace is running the algorithm by hand on a tiny input and writing down the state after every step. It is the single most useful debugging habit there is, because it shows you the exact step where your reasoning and the machine's behaviour part company.

Three steps, and you can see the answer appear. Now imagine the list had a thousand items — you would not trace it by hand, but you would still reason about it the same way. That is what the rest of this course is about.

4Break it down, then check the edges

Decomposition is the habit of splitting a hard problem into smaller problems you already know how to solve. "Find the tallest person in the room" becomes "compare two people, keep the taller, repeat". Each piece is obvious; the whole thing was not.

Then check the edge cases — the inputs at the boundary. What if the list is empty? What if it has one item? What if every item is the same? Bugs live almost exclusively in these corners, and they are cheap to check on paper.

✓ Your win for today

You can now take a vague task and turn it into a numbered list of steps that a machine could follow without understanding anything — and you can trace that list by hand to prove it works. Every algorithm in this course is built on exactly that move.

5Do this next

  1. Write pseudocode for "find the largest number in a list". Use a variable called best and a loop. Do not write code yet.
  2. Trace your algorithm on [4], then on []. What does it do when there is nothing to compare? Fix it if the answer is nonsense.
  3. Write pseudocode for making a cup of tea, then hand it to someone and watch them follow it literally. Every place they hesitate is a step you left ambiguous.
Primary source Read _Introduction to Algorithms_ by Cormen, Leiserson, Rivest & Stein, Chapter 1 ("The Role of Algorithms in Computing"). It is the standard reference for the whole subject, and Chapter 1 is short, non-mathematical, and exactly this lesson in more detail.
