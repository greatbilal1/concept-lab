Lesson 09 · Putting it together

Where procedural breaks down

Procedural programming is not wrong — it is limited. This lesson is about the exact point where the style starts to strain, so you can recognise it in your own code instead of discovering it the hard way.

Time ~10 min Win Recognise the procedural limit in real code Mission link Know when to reach for something else

1The same data, passed everywhere

The first sign of strain is a group of values that always travel together. Here name, email, and plan are passed to every procedure as three separate parameters. 

def send_welcome(name, email, plan):
    ...

def send_invoice(name, email, plan):
    ...

def upgrade(name, email, plan):
    ...

This is a data clump: a set of values that belong together but have no name. Every procedure repeats the same three parameters, and adding a fourth means editing every one of them.

2Coupling between steps

The second sign is coupling: procedures that know too much about each other. When one procedure must be called before another, or must be passed the exact shape the other expects, the steps are no longer independent. 

def load_user():
    return {"name": "Ada", "email": "a@x.com", "plan": "pro"}

def send_invoice(user):
    # must know the exact keys load_user produces
    print(user["name"], user["email"], user["plan"])

The dictionary helps — the clump now has one name, user — but the two procedures are still coupled through its exact shape. Change a key in one and the other breaks silently.

Watch out A dictionary is a step towards a fix, not the fix itself. It groups the data, but nothing stops a procedure from using the wrong key or leaving one out.

3The procedural limit

The procedural limit is this: procedures operate on data, but the data has no procedures of its own. The behaviour that belongs to a user — sending them a welcome, invoicing them, upgrading them — lives far away from the user data, in free-floating procedures. 

# the data
user = {"name": "Ada", "email": "a@x.com", "plan": "pro"}

# the behaviour, somewhere else entirely
send_welcome(user)
send_invoice(user)
upgrade(user)

Nothing ties the two together. A new reader has to search the whole file to find every procedure that touches a user. That is the strain — and it is exactly what the next course, Object-Oriented Programming, is built to relieve.

✓ Your win for today

You can name the procedural limit: data and the behaviour that belongs to it live in different places. That is not a bug in your code — it is the edge of the style. The next lesson puts the whole course together, and points at what comes after.
