Lesson 08 · Wasm Beyond the Browser & WASI

Beyond the Browser: WASI & Server-Side Wasm

'If WASM + WASI had existed in 2008, we wouldn't have needed to create Docker' — Solomon Hykes (co-founder of Docker). Discover serverless Wasm.

Time ~10 min Win Explain the WebAssembly System Interface (WASI) and run standalone Wasm binaries with Wasmtime and Node.js Mission link Deploy ultra-lightweight, sandboxed microservices and edge compute functions using WASI

1WebAssembly outside the browser

WebAssembly was designed for browsers, but its core properties—near-native speed, compact size, instant startup (<1ms), and capability-based security sandboxing—make it an extraordinary runtime for cloud servers and edge compute.

Docker containers require bundling an entire mini-Linux operating system (megabytes or gigabytes in size). A server-side Wasm module is typically a few hundred kilobytes, starts in microseconds, and consumes almost zero idle RAM.

Key idea Server-side WebAssembly provides sub-millisecond cold starts and sandboxed execution with zero OS container bloat.

2WASI: WebAssembly System Interface

The WebAssembly System Interface (WASI) defines a modular, standard collection of POSIX-like system APIs: reading files, querying clocks, and generating random numbers.

Crucially, WASI uses capability-based security: a WASI module has zero access to files by default. The host runtime (like Wasmtime, Wasmer, or Node.js) must explicitly grant access to specific directories (e.g. wasmtime run --dir=/tmp app.wasm).
