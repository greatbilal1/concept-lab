CQRS: Command Query Responsibility Segregation

Why use the same data model for writing transactions and rendering search dashboards? Master CQRS: separating write-optimized models from read-optimized views.

Time ~10 min Win Architect systems using Command Query Responsibility Segregation (CQRS) Mission link Eliminates database contention between write transactions and complex analytical queries

1Asymmetric data models

In traditional architectures, the same database schema is used for both writing data and reading data. But writes need normalization (3NF) to prevent anomalies and enforce ACID integrity. Reads need denormalization with pre-joined data to serve complex UI dashboards in milliseconds!

Greg Young formalized CQRS (Command Query Responsibility Segregation): split your application into two completely separate models. The Command Model handles writes, business validation, and updates the write database. The Query Model reads from a denormalized read-optimized store (like Elasticsearch or Redis) projected asynchronously from write events!

Key idea CQRS separates the write model (optimized for consistency) from the read model (optimized for speed).
