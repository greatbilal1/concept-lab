ARIA: Roles, States & The First Rule

ARIA is powerful, but dangerous when misused. Learn the First Rule of ARIA and how to apply roles, states, and properties correctly.

Time ~10 min Win Apply WAI-ARIA roles, states, and properties appropriately while prioritizing native semantic HTML Mission link Prevent catastrophic ARIA misconfigurations that break assistive technology functionality

1The First Rule of ARIA

The official W3C specification begins with a startling statement: "If you can use a native HTML element or attribute with the semantics and behavior you require, then do so! Do NOT use ARIA!"

Why? Because ARIA only changes the accessibility representation in the AOM; it adds zero behavior. Writing <div role="button"> does not make the div focusable with Tab, and does not trigger click on Enter or Space. You must write 40 lines of JavaScript to recreate what <button> provides out of the box.

Key idea No ARIA is better than bad ARIA. Always prefer native HTML elements.

2Roles, States, and Properties

When native HTML cannot express a complex widget (like an accordion, tabs, or modal dialog), ARIA fills the gap with three categories:

  • Roles: Define what an element is (e.g. role="dialog", role="tab", role="progressbar"). Roles do not change after creation.
  • States: Dynamic attributes that change frequently (e.g. aria-expanded="false", aria-selected="true", aria-busy="true").
  • Properties: Characteristics less likely to change (e.g. aria-haspopup="dialog", aria-controls="panel-1").
