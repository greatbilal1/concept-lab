Lesson 02 · Accessibility Foundations & Assistive Tech

The Accessibility Tree & Native Semantics

Browsers create two trees: the DOM Tree for visual rendering, and the Accessibility Tree for assistive devices. Learn how they sync.

Time ~10 min Win Inspect the browser Accessibility Tree and compute an element's Role, Name, State, and Value Mission link Guarantee that interactive UI elements communicate their purpose clearly to assistive software

1The parallel tree: DOM vs AOM

When a browser parses an HTML document, it constructs the DOM Tree (Document Object Model) to compute styling and layout. In parallel, it creates the Accessibility Tree (often called the Accessibility Object Model or AOM).

Assistive technologies do not inspect CSS pixels. They query the Accessibility Tree. Every accessible node has four essential properties:

  • Role: What the element is (e.g. button, heading, checkbox).
  • Name: The label identifying this specific element (e.g. "Submit Order").
  • State: Current condition (e.g. checked, expanded, disabled).
  • Value: Current data quantity (e.g. 50% in a progress bar).
Key idea The Accessibility Tree exposes Role, Name, State, and Value to assistive tech; styling does not affect accessibility.

2How Accessible Names are computed

The Accessible Name Computation algorithm calculates an element's label following a strict hierarchy of precedence:

  1. aria-labelledby (references another element's ID).
  2. aria-label (direct string attribute).
  3. Native element label (e.g. <label for="..."> on inputs, or alt on images).
  4. Subtree text content (the text inside the button).
  5. title attribute (weakest fallback).
