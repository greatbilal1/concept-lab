Lesson 05 · Unit of Work & Identity Map

Unit of Work and the Identity Map

How does an ORM know what changed without querying the database? Discover the Unit of Work pattern, dirty checking, the Identity Map, and session flushes.

Time ~10 min Win Explain the Unit of Work lifecycle, dirty checking, and Identity Map deduplication Mission link The architectural core of enterprise Data Mapper ORMs like SQLAlchemy and Hibernate

1The in-memory transaction sandbox

In modern Data Mapper ORMs, when you load an entity and modify user.email = 'new@email.com', the ORM does not immediately send an UPDATE to the database. Instead, it operates inside a Unit of Work pattern managed by the Session.

The session tracks all loaded objects in an Identity Map. When you call session.commit(), the Unit of Work performs dirty checking (comparing current values against loaded snapshots), calculates the minimal SQL statements needed, orders them to satisfy foreign keys, and flushes them in a single batch.

Key idea Unit of Work batches changes and flushes minimal SQL statements atomically upon commit.
