Lesson 03 · The N+1 Problem & Loading

The N+1 query problem and eager loading

The #1 performance killer in modern web applications. Discover why lazy loading turns a single page render into 500 individual database queries, and how to fix it with eager loading.

Time ~10 min Win Diagnose and eliminate N+1 query storms using eager loading and joined loads Mission link The single most common database performance bug in web application development

1The accidental query storm

Consider rendering a list of 100 blog posts with their author names. You query all posts: posts = Post.all() (1 query). Then in your template loop, you write: for p in posts: print(p.author.name).

Because author is lazy-loaded, the ORM fires a separate query for every single post: SELECT * FROM authors WHERE id = ?. 1 initial query + 100 author queries = 101 queries (N+1)! A page that should take 5ms now takes 2 seconds.

Key idea The N+1 problem occurs when lazy-loading related entities inside a loop, firing N extra queries.

Contrast lazy query storms with high-performance eager loading strategies.

3Tracing the N+1 fix with joinedload

Trace how instructing the ORM to eager load collapses 101 queries down to a single JOIN.

4Practice

Test your memory of the N+1 query problem.

✓ Your win for today

You can detect N+1 query storms in application logs and eliminate them using eager loading joins or prefetching.

5Do this next

  1. Enable SQL logging in your ORM to observe the queries emitted during a page render.
  2. Identify an N+1 query loop and fix it using eager loading (joinedload, select_related, or include).
  3. Install an automated N+1 detection tool (like django-debug-toolbar or bullet gem).
