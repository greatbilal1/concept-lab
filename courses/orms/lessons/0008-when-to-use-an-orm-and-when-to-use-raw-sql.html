Lesson 08 · Migrations & Trade-offs

When to use an ORM and when to use raw SQL

ORMs are great for OLTP CRUD, but terrible for bulk analytics and complex reports. Master the pragmatic spectrum: ORMs, Query Builders, and raw parameterized SQL.

Time ~10 min Win Select between ORMs, Query Builders, and raw SQL based on performance and complexity Mission link Fosters pragmatic engineering judgment over dogmatic tool loyalty

1The pragmatic spectrum

Junior developers argue over ORM versus raw SQL as an all-or-nothing religious war. Senior engineers treat them as a spectrum of tools suited for different jobs.

ORMs excel at: Interactive OLTP web apps, single-row CRUD, form validation, and schema migrations. Raw SQL / Query Builders excel at: Bulk updates (updating 100,000 rows in one query), complex analytical reporting with window functions, performance-critical hot paths, and multi-table aggregations.

Key idea Use ORMs for transactional CRUD; drop to raw SQL or query builders for bulk operations and analytics.

2The database interaction spectrum

Choose the right level of abstraction for each specific database requirement.

3Tracing the memory cost of object inflation

Trace why instantiating 100,000 ORM class instances consumes 800 MB of RAM while raw tuples use 15 MB.

4Practice

✓ Your win for today

You can wield ORMs effectively for domain logic while fluently dropping to raw SQL for high-throughput batch operations.

5Do this next

  1. Benchmark the memory usage of loading 10,000 rows via an ORM versus raw database driver tuples.
  2. Refactor an inefficient loop of individual ORM updates into a single bulk UPDATE query.
  3. Experiment with a modern lightweight query builder like Kysely or SQLAlchemy Core.
