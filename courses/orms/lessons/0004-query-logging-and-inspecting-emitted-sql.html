Lesson 04 · The N+1 Problem & Loading

Query logging and inspecting emitted SQL

Never trust an ORM blindly. Learn how to configure SQL query logging, read the emitted SQL statements, and identify hidden performance disasters.

Time ~10 min Win Enable SQL logging in ORMs and evaluate emitted statements for inefficiencies Mission link The essential debugging practice for validating ORM behavior

1Peeking behind the magic curtain

An ORM is a code generator: you write high-level method calls, and the ORM translates them into SQL strings sent over the wire. If you never look at those SQL strings, you are flying blind.

Every professional developer enables SQL Query Logging in development. By watching your terminal console, you instantly spot redundant queries, missing indexes, Cartesian product joins, and columns selected that you never use.

Key idea Always enable SQL query logging in development: inspect what the ORM is actually emitting.

2What to look for in ORM logs

Learn the three common red flags to look for when inspecting emitted SQL logs.

3Tracing query emission in terminal logs

Trace how a single ORM call prints its compiled SQL query and bound parameters.

✓ Your win for today

You can configure SQL logging, inspect emitted queries, and catch performance bottlenecks before code reaches production.

5Do this next

  1. Enable echo=True in your local ORM configuration and watch the queries generated by your app.
  2. Identify an endpoint that emits more than 10 SQL queries for a single HTTP request.
  3. Verify that your ORM parameterizes variables rather than string-concatenating them.
