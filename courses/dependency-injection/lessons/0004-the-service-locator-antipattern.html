The Service Locator antipattern

The dark twin of Dependency Injection. Discover why the Service Locator pattern obscures class dependencies, creates runtime null crashes, and defeats compiler safety.

Time ~10 min Win Identify and refactor the Service Locator antipattern into explicit constructor injection Mission link Prevents hidden dependencies from causing unexpected runtime crashes

1The disguised global variable

At first glance, a Service Locator looks like dependency injection: you have a central registry (ServiceLocator.get('Database')). Instead of passing dependencies in the constructor, a class reaches out to the global locator to fetch what it needs.

Mark Seemann and Martin Fowler classify Service Locator as a dangerous Antipattern. Why? Because it hides a class's true dependencies! When you instantiate new OrderService(), the constructor takes zero arguments, lying to you that it has no dependencies. Then at runtime, it suddenly crashes because someone forgot to register the database in the global locator!

Key idea Service Locator hides dependencies and defers missing-dependency errors to runtime crashes.

2Constructor Injection versus Service Locator

Contrast honest, explicit constructor signatures with deceptive, hidden Service Locator lookups.

✓ Your win for today

You can spot the Service Locator antipattern in legacy code and refactor it into honest, explicit constructor injection.

5Do this next

  1. Audit a class that calls a global ServiceLocator or Container.get() inside its methods.
  2. Refactor the class to accept those dependencies as constructor parameters.
  3. Observe how the refactored class can be instantiated in tests without setting up global container state.
