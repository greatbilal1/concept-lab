Lesson 08 · Testability & Test Doubles

When DI becomes over-engineering

Should you inject the string library? Discover when dependency injection crosses the line into over-engineering, and the pragmatic boundaries of simplicity.

Time ~10 min Win Identify when dependency injection is unnecessary and apply pragmatic YAGNI boundaries Mission link Prevents architectural bloat and preserves simplicity in software codebases

1The abuse of abstraction

Like any good design principle, Dependency Injection can be taken to absurd extremes. Some developers create an IStringConcatenator interface, an IConsoleWriter, and an IMathAdder, injecting basic language operations through a 500-line DI container!

This is architecture astronautics. The rule of thumb: Stable, deterministic, pure mathematical operations should NOT be injected. You inject volatile collaborators (databases, networks, time, randomness, external APIs). You do not inject basic data structures, math libraries, or pure utility functions.

Key idea Inject volatile dependencies that touch I/O or external systems; never inject pure deterministic utilities.

2What to inject versus What to call directly

Categorize dependencies into volatile collaborators (inject) versus stable utilities (direct call).

3Tracing over-engineered DI bloat

Trace how removing an unnecessary interface simplifies code without losing any testability.

4Practice

Test your memory of pragmatic DI boundaries.

✓ Your win for today

You can apply dependency injection with pragmatic discipline, knowing exactly when to inject and when to keep code simple.

5Do this next

  1. Audit your DI container to see if any pure utility functions are being unnecessarily injected.
  2. Remove an interface that has only one implementation and will never have another.
  3. Explain the difference between a volatile collaborator and a stable dependency to a colleague.
