IaC in CI/CD & GitOps Pipelines

Never run 'terraform apply' from a developer laptop in production. Automate delivery through GitOps pipelines.

Time ~10 min Win Design an automated GitOps CI/CD pipeline for Terraform with automated planning, reviews, and applies Mission link Eliminate human operational errors and deploy infrastructure reliably across environments

1The danger of laptop applies

Running terraform apply directly from an engineer's laptop introduces massive operational risks: local differences in Terraform versions, uncommitted local edits, personal cloud credential leaks, and zero peer visibility.

In a mature GitOps pipeline, the only entity permitted to execute terraform apply is the automated CI/CD pipeline (e.g. GitHub Actions, GitLab CI, Atlantis, or Spacelift). Humans open Pull Requests; machines test, plan, and apply.

Key idea All production infrastructure changes must flow through version control and be executed by automated CI/CD pipelines.

2The standard GitOps workflow for IaC

A production GitOps pipeline follows strict stages:

  1. Branch & Edit: Engineer creates a branch and edits .tf files.
  2. Validation: CI runs terraform fmt -check, terraform validate, and checkov.
  3. Plan generation: CI runs terraform plan and posts the diff as a comment on the Pull Request.
  4. Peer Review: Tech lead approves the PR after inspecting the exact plan.
  5. Merge & Apply: Merging to main triggers the CI runner to execute terraform apply.
