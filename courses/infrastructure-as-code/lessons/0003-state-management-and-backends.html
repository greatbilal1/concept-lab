Lesson 03 · Terraform Primitives, Providers & State

State Management & Backends

Terraform's state file is the single source of truth mapping your code to real-world cloud resources. Learn how to protect and lock it.

Time ~10 min Win Configure remote backends with state locking and manage state safely across collaborative engineering teams Mission link Prevent corrupted state files and concurrent apply race conditions in multi-engineer teams

1Why Terraform needs state

When you declare resource "aws_instance" "web", Terraform must record that this code block corresponds to the real-world cloud ID i-0a8b9c1d2e3f in AWS.

This mapping is stored in the Terraform State file (terraform.tfstate). The state file also caches metadata, resource dependencies, and sensitive output values. If you lose the state file, Terraform forgets what it owns and attempts to create duplicate resources on the next apply.

Key idea The state file maps declarative code identifiers to real-world cloud IDs; without state, Terraform cannot manage existing resources.

2Remote backends and state locking

By default, Terraform stores state on your local laptop disk (local backend). In a team, this is disastrous: changes made by engineer A are unknown to engineer B.

A remote backend (e.g. AWS S3, Google Cloud Storage, Terraform Cloud) stores the state in a central, encrypted bucket. To prevent two engineers from running terraform apply at the same second (which corrupts state), backends provide state locking (e.g. via DynamoDB).
