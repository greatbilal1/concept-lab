Lesson 07 · Accessibility & Inspection

Accessibility roles and ARIA basics

Accessibility is not a feature; it is the web working as designed. Learn how the browser constructs the Accessibility Tree and when to use ARIA attributes.

Time ~10 min Win Apply ARIA roles and labels to enhance accessibility without violating standard semantics Mission link Ensures applications are fully operable by users of assistive technology

1The Accessibility Tree

In parallel with the visual DOM, the browser builds an Accessibility Tree for operating system assistive technologies (screen readers, braille displays). Every accessibility node has four properties: Role (what is it?), Name (what is it called?), Value, and State.

The golden rule of accessibility: The first rule of ARIA is do not use ARIA if a native HTML element exists. A native <button> has keyboard focus, enter key submission, and role button built in; a <div role="button"> has none of these unless you implement them manually.

Key idea Native semantic HTML provides built-in accessibility roles, states, and keyboard navigation for free.

2When ARIA is required

Use ARIA when building custom widgets (like modals or tabs) that native HTML does not natively provide.

3Tracing accessibility tree inspection

Trace how a screen reader interprets an icon button with an aria-label.

4Practice

Test your recall of accessibility fundamentals.

✓ Your win for today

You can build custom interactive components that communicate clear names, roles, and states to assistive technologies.

5Do this next

  1. Inspect the Accessibility Tree of a website using the Accessibility tab in Chrome/Firefox DevTools.
  2. Navigate your application using only the Tab and Enter keys on your keyboard.
  3. Add an aria-label to any button that contains only a visual icon.
