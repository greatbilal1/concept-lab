Workload Identity Federation (IAM Roles for Service Accounts)

Keyless cloud access: OpenID Connect (OIDC), AWS IRSA (IAM Roles for Service Accounts), GCP Workload Identity, and GitHub Actions keyless deploys.

1Core principles of Workload Identity Federation (IAM Roles for Service Accounts)

Historically, to deploy code from GitHub Actions to AWS, developers generated a permanent `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` and saved them in GitHub Secrets. If those secrets leaked, attackers gained permanent access to your cloud infrastructure.

Key idea Keyless cloud access: OpenID Connect (OIDC), AWS IRSA (IAM Roles for Service Accounts), GCP Workload Identity, and GitHub Actions keyless deploys.

3Static Keys vs Workload Identity

  • 1. The Keyless Handshake: When a GitHub Actions workflow runs, GitHub's internal OpenID Connect (OIDC) provider signs an ephemeral identity token proving: 'This request is from repository:company/app, branch:main'.
  • 2. Trust Relationship in AWS: AWS IAM is configured to trust GitHub's OIDC certificate authority.
  • 3. Token Exchange: GitHub Actions sends the signed OIDC token to `sts:AssumeRoleWithWebIdentity`. AWS verifies GitHub's cryptographic signature and returns temporary 1-hour credentials!
  • 4. Zero Stored Secrets: There is no static API key stored in GitHub Secrets. There is nothing to leak, nothing to steal, and nothing to rotate!
# Keyless GitHub Actions Deployment to AWS (OIDC YAML):
name: Deploy to Production
on:
  push:
    branches: [main]
permissions:
  id-token: write # Mandatory: Allows requesting OIDC JWT from GitHub!
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Authenticate with AWS via OIDC (ZERO STATIC SECRETS!)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubDeployerRole
          aws-region: us-east-1
      - name: Deploy to Cloud
        run: aws s3 sync ./dist s3://company-production-assets

The Keyless Cloud Revolution: Never create long-lived IAM user access keys for CI/CD or Kubernetes. Use Workload Identity Federation with OIDC.
