The Principle of Least Privilege: Scoping IAM Roles

Access governance: the Principle of Least Privilege (PoLP), AWS IAM policy design, resource-level scoping, and eliminating wildcard ('*') permissions.

Time ~10 min Win You know how to design least-privilege IAM policies and eliminate dangerous wildcard permissions. Mission link Mastering the principle of least privilege: scoping iam roles across modern software engineering

1Core principles of The Principle of Least Privilege: Scoping IAM Roles

When setting up AWS IAM or cloud permissions, junior developers often attach AdministratorAccess or use wildcards: Action: "s3:*", Resource: "*" because 'it makes everything work without permission errors'. This is the security equivalent of giving the office janitor the nuclear launch codes.

Key idea Access governance: the Principle of Least Privilege (PoLP), AWS IAM policy design, resource-level scoping, and eliminating wildcard ('*') permissions.

2Wildcard Disaster vs Least-Privilege Policy

If a microservice with wildcard permissions is compromised via a dependency exploit, the attacker has complete control over your entire cloud infrastructure.

3Limiting Blast Radius

Engineering Least-Privilege IAM Policies:

  • 1. Explicit Allowed Actions: Never use `s3:*` or `dynamodb:*`. Specify the exact required API operations: `["s3:GetObject", "s3:PutObject"]`. Deny `s3:DeleteBucket` and `s3:PutBucketPolicy`!
  • 2. Resource-Level Scoping: Never use `Resource: "*"`. Scope permissions to the exact target ARN: Resource: "arn:aws:s3:::company-invoices-prod/*".
  • 3. Separation of Read and Write Roles: A data extraction service needs `s3:GetObject`, not write access. A logging service needs `s3:PutObject`, not read access.
  • 4. Condition Keys: Restrict actions by source IP, mandatory MFA, or secure transport: Condition: {"Bool": {"aws:SecureTransport": "true"}}.
# SECURE Least-Privilege IAM Policy (JSON):
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowInvoiceReadingOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::company-invoices-prod/inbound/*",
      "Condition": {
        "Bool": {"aws:SecureTransport": "true"}
      }
    }
  ]
}

The Wildcard Ban: In production IAM policies, treat "*" as a critical security smell. Always scope actions and resource ARNs explicitly.
