Lesson 05 · Keyed lookup

Hash tables

An array is fast when you know the index. But most of the time you do not — you know a name. A hash table closes that gap: it turns a key into an index, so lookup by name is as fast as lookup by position.

Time ~10 min Win Explain collisions and why resizing keeps lookups fast Mission link Turning a key into an address

1From key to slot

A hash table is an array underneath, plus one extra idea: a hash function that converts a key into an array index. Give it the key "alice" and it hands back a number like 3. Store the value at slot 3, and later you can find it again by hashing the same key.

The same key always produces the same index — that is the only guarantee the hash function has to make. It does not need to be random or reversible, just consistent.

Key idea A hash table trades a little computation (hashing the key) for a huge saving (jumping straight to the right slot instead of searching).

2Collisions

Two different keys can hash to the same slot. This is a collision, and it is not a bug — with a finite table and unlimited possible keys, collisions are guaranteed. The question is only how you handle them.

The common answer is chaining: each slot holds a small list, and colliding keys simply share the slot. Lookup hashes the key, goes to the slot, then scans the short list: 

slots[3] = [("alice", 30), ("bob", 25)]
# hash("alice") -> 3, then scan the list

The other answer is probing: if the slot is taken, look at the next one, and the next, until you find a free space.

3Load factor and resizing

As you add items, the slots fill up and the chains grow longer. The ratio of stored items to slots is the load factor. When it climbs too high, lookups slow down — a chain of ten items is a linear scan.

So the table resizes: it allocates a bigger array and rehashes every key into it. That single operation is expensive, but it happens rarely, so the amortised cost of an insert stays near constant.

Why this matters Resizing is why hash tables can promise O(1) average lookup while still occasionally doing O(n) work. The average is what you feel in practice.

4Python's dict

You have been using a hash table all along. Python's dict is one, written {key: value}. Lookup, insert and delete are all near-constant time on average: 

ages = {"alice": 30, "bob": 25}
ages["alice"]        # 30 — hash the key, jump to the slot
ages["carol"] = 41   # insert
"bob" in ages        # True — membership is a lookup

The catch: keys must be hashable — immutable and consistent. Strings, numbers and tuples qualify; lists do not, because a list can change after you hash it.

✓ Your win for today

You can explain how a key becomes an index, why collisions are unavoidable, and how chaining and resizing keep lookups fast. You also know that dict is a hash table, and why its keys must be immutable.
